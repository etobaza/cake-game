# Architecture

## Repository guidance

Repository content is English-only: documentation, memory notes, source comments, user-facing strings, tooling, and generated reports follow the mandatory [repository language rule](AGENTS.md#repository-language-mandatory). Generators must preserve this rule when rebuilding their output.

`AGENTS.md` is the shared session/startup and verification contract. `CODE_STYLE.md` defines Luau conventions for new and touched code; `PACKAGES.md` maps the actual dependencies and call-site boundaries. `CLAUDE.md` and `GEMINI.md` import the shared rules, while `.github/copilot-instructions.md` directs Copilot to them and includes the core verification requirements. Cursor uses root `AGENTS.md` directly. Zed's filename precedence selects the Copilot entry here, which directs it to the shared rules. `AI_INSTRUCTIONS.md` records discovery behavior, limitations, and new-session checks. Keep these entry files thin instead of maintaining independent architecture copies.

Generated sourcemaps, installed Wally packages, logs, temporary files, editor backups, and operating-system metadata are excluded through `.gitignore`. Keep dependency manifests and lock files under version control.

Reference research lives in [Exeperience/LemonCake](Exeperience/LemonCake/README.md), with a short retrieval guide in [mem/lemon-cake.md](mem/lemon-cake.md). The Lemon Cake snapshot records Steam build identity, extracted data, Blueprint indexes, reproduction tools, and verification limits. Original extracted assets and full dumps stay in its ignored `.local` cache. These folders are documentation/research tooling, not Roblox runtime source roots; the reference does not override this project's architecture or adapted balance.

## Runtime layout

The repository mirrors Roblox DataModel services on disk. Studio's Script Sync keeps the place and this folder in step (scripts only; it maps directories literally, so a directory holding `init.luau` is that script with its siblings as children, and `.client` / `.server` / `.legacy` suffixes pick the script class). `.vscode/generate-sourcemap.ps1` applies the same rules to produce `sourcemap.json` for the Luau Language Server, so the gate works with Studio closed. Script Sync also writes its own `sourcemap.json` (absolute paths) whenever it syncs; the two are interchangeable for luau-lsp, and neither is edited by hand or committed.

`StarterCharacterScripts` and `StarterPlayerScripts` live at the repository root and are mapped under `StarterPlayer`.

- `ReplicatedStorage/Client.client.luau` is the client bootstrap. It loads `CmdrClient` when present, registers every direct child module of `ReplicatedStorage/Handlers` with Crystal, then calls `Crystal.Run()`.
- `ServerScriptService/Server.legacy.luau` is the server bootstrap. It registers Cmdr hooks, types, and commands from `ServerScriptService/Cmdr`, registers every direct child module of `ServerScriptService/Handlers` with Crystal, then calls `Crystal.Run()`.
- `ReplicatedStorage/Handlers` contains client handlers. `ServerScriptService/Handlers` contains server handlers. Crystal loads a handler only when it is a direct `ModuleScript` child of those folders; nested modules are required by their handler.
- `AmbientMotionHandler` loads shared clips from `ReplicatedStorage.Assets.Animations.Ambient`, skipping non-`KeyframeSequence` children and unreadable clips with loop guards. Missing clips do not prevent visual setup; a missing folder prints a diagnostic message.
- `ReplicatedStorage/Shared` contains code and data safe to require from either runtime: Crystal, the bus, configs, UI, shared gameplay views, and utility libraries.
- `ReplicatedStorage/Shared/Libs` holds `Logger` and `StateMachine` (project code) next to vendored third-party libraries: `Packet`, `PartCache`, `Ripple`, and `Signal`. The vendored ones are committed as-is and excluded from lint and type analysis.
- `ServerScriptService/Cmdr` contains Studio/admin command definitions. The client command surface is `ReplicatedStorage/CmdrClient`, created by Cmdr at runtime.

## Authored assets

Authored content ships as Roblox Packages (`PackageLink`) and lives in the place: `Workspace.World` (bakeries, environment, roofs, and spawn), `ReplicatedStorage.Assets` (prompt billboard, animations, model templates, source art, and VFX), and `StarterGui.MainGui` (every ScreenGui). These package roots add a wrapping folder, and code addresses the contents relative to it:

- `ReplicatedStorage/Shared/World.luau` is the only place that knows the world package's location. `World.Root` / `WaitForRoot` find `Workspace.World`; `World.Bakeries` and `World.Find(path)` resolve below it. Configs that name world content (`Base.BakeriesFolderName`, `Traffic.RoadPath`, `Traffic.Signals.Path`, `Guests.Street.SidewalkPath`) are child-name paths relative to that root, never to `Workspace`. Templates that are cloned rather than placed (building models, food, tools, traffic vehicles, and cats) live under `ReplicatedStorage.Assets.Models`. Anything else the game needs from the world must go through this module rather than `workspace:FindFirstChild`.
- `ReplicatedStorage.Assets.Models.Cats` contains the four original `cat` rigs. `CatHandler` reads the folder named by `Cats.TemplatesFolder` and keeps its existing MeshId sort, preserving saved variant indices. Its prepared runtime copies remain in `ServerStorage.CafeCatTemplates`; spawned cats belong to their bakery. The `Scratch` slot has no authored clip: the client pitches the body nose-up around the hind feet (`Cats.ScratchPitch`, `ScratchPivot`) so the front paws rest on the post, and the slot offset keeps the head clear of it.
- Cat length follows the installed Lemon Cake build 6596857 ratio to its cat tree: `SK_Cat` imported length 171.246643, multiplied by `BP_Cat.Cat` scale 0.85, divided by `SM_CatTree` height 173.489883 and `BP_CatCafe.SM_CatTree` scale 1.075. `SpawnCats` bytecode at offsets 886 and 1142 explicitly uses unit actor scale; the location marker's 0.5 X scale does not shrink the cat. The resulting `Cats.LengthToTreeHeight` is 0.780474, giving a 3.868-stud cat beside the authored 4.956-stud tree (previously 2.4). All slots use the tree as the common size reference. This matches relative length while preserving the supplied Roblox rig's proportions; poses and meshes differ from the original. Source packages are in the ignored reference extraction under `Exeperience/LemonCake/.local/json/Art/Mesh/Animal`, `Art/Mesh/Furniture` and `Blueprints/Shop`; `SK_Cat` bounds are seven little-endian floats after the two strip-flag bytes in its decoded `Extras`, consistent with [CUE4Parse skeletal-mesh deserialization](https://github.com/FabianFG/CUE4Parse/blob/master/CUE4Parse/UE4/Assets/Exports/SkeletalMesh/USkeletalMesh.cs).
- `ReplicatedStorage.Assets.SourceModels` preserves the remaining 105 artist originals formerly staged in `Workspace.World.Assets`, including duplicate names and the original cake folder. This reference-art collection is outside `Models` so `Buildings.FindAsset` cannot accidentally select an unprepared duplicate. Names, pivots, meshes, and existing prepared model paths are preserved. The embedded plant animation script is disabled in this collection (`SourceTemplateWasEnabled` records its previous state), so stored source art does not animate. Promote usable templates into the appropriate `Models` category deliberately. Asset reparenting and script enabled state are place changes; Script Sync does not serialize them, so save the edited place separately from the source commit.
- `UIHandler` waits for `PlayerGui.MainGui` (`SCREENS_FOLDER`) and hands that folder to `Shared/UI/App` as the root that all screens are looked up under. Nothing else looks up an authored screen by name in `PlayerGui`; drivers go through `UIHandler:GetPanel` / `GetHud`.
- `MenuHandler` preserves the authored empty selected-recipe plate's darker background, border, geometry, font, and text color. Its caption reads `Empty`, with both text layers horizontally centered inside the centered status container. Empty plates remain passive placeholders without a food viewport and continue toggling with the existing filled plates as recipes are selected.
- `RecipePickHandler` fits the recipe list to its authored container and centers the existing rows with a permanent scrollbar inset. Eight logical pixels above and below the list protect selection outlines from clipping. Its canvas follows the list layout's visible content height, converted out of `UIScale`, plus both edge insets so the last row remains reachable after menu or viewport changes.
- `MenuHandler` gives both dietary bonus states matching 24-pixel logical rows with a 4-pixel gap and a shared left edge. The footer reserves additional space in wide, compact, and short layouts by moving or shortening the selected-recipe strip and reducing the recipe grid where needed; earned/unearned visibility and bonus values remain unchanged. Local preparation helpers own status text, bonus row styling, and responsive footer geometry; `CollectBonuses` identifies and stores the earned/unearned pairs.

Captions and numbers have matching 20-pixel logical side insets and a reserved gap between their columns. Row text uses a 32-pixel logical maximum, headings and profit text use 34, and paired labels are vertically centered and shrink to fit their available width. It hides the old `Middle.Lines` dashed inset, which would otherwise draw over the first and last rows. It updates the existing responsive size attributes and text baselines so viewport changes preserve the larger layout; the fixed report canvas does not grow with its scaled rows.
- `Shared/UI/BakeryMenu` owns the shared header for Report, Menu, and Upgrades. During `Summary`, the header shows only Report, Menu, and Next Day in three equal-width slots, vertically centered with 8-pixel logical gaps. The outer tab edges align with the page background's 6-pixel logical side insets. The existing ribbon artwork extends 64 logical pixels to the left so its triangular tail sits outside the page; the header moves up 22 logical pixels, leaving an 8-pixel gap above the page background. An explicit right anchor and matching wide/compact row sizes and header positions preserve alignment after resizing; each tab's dashed inset is centered as well. The row reclaims the hidden close button's space; `ReportHandler` permits only Report and Menu in the evening modal, so Upgrades cannot open through the HUD either. Outside that phase, HUD-opened pages bind the authored full-size `Header.Title` from StarterGui, with the existing close control. Upgrades remains available through the HUD outside the evening modal.
- `StarterGui.Mikey` supplies the authored visual reference for `StarterGui.MainGui`. Matching controls use its colors, fonts, backgrounds, corners, strokes (including stroke sizing mode), and gradients directly in the place. Report and the shared bakery header reuse that palette and decoration. The appearance pass preserves outer panel dimensions and gameplay layouts. Internal Funds, reward-card, recipe-card, and ribbon proportions follow the reference within those dimensions. Semantic icons use `ScaleType.Fit`; tiny rotations are removed from scrolling content to preserve clipping. Selection outlines respect authored scaled stroke thickness. Reference ScreenGuis under `Mikey` stay disabled so their sample HUD does not overlap the live HUD. Place asset changes must be saved with the place separately from Script Sync source.
- `ReplicatedStorage.Assets.VFX` holds one flat `BasePart` per effect named in `Configs/VFX.Effects` (plus `OvenFire`), carrying the emitters and the placement attributes `VFXHandler` reads (`SourceOffset`, `SourceFoodSize`, `SourceToolSize`, `BodyOffset`). ## Dependencies

Wally owns every registry package. `ReplicatedStorage/wally.toml` lists the shared-realm packages (`cmdr`, `flux`, `janitor`, `topbar-plus`, `typed-promise`) and installs into `ReplicatedStorage/Packages`; `ServerStorage/wally.toml` lists the server-realm packages (`profilestore`) and installs into `ServerStorage/ServerPackages`. Both install directories are gitignored; the manifests and lock files are committed.

Run `scripts/install-packages.ps1` after cloning or changing a manifest. It installs both manifests into a unique temporary directory outside the synced project, then flattens each package into the layout Script Sync understands: Wally emits Rojo projects (`_Index/<package>/<name>/default.project.json` pointing at `src/`, `lib/`, or one file), which Script Sync would mirror as a Folder and break every link `require`. Flattening keeps the mapped runtime root, discards the surrounding development/test tree, moves that root up so `<name>/init.luau` is the package, drops non-script files, and renames `.lua` to `.luau`. The installer verifies every package root, generates a temporary sourcemap, and runs `wally-package-types` before replacing the watched package directories with the complete trees. It then copies back the lock files and regenerates the project sourcemap. Failed installation restores the previous package directories. Never install or flatten raw Wally output inside the watched directories: Script Sync can import intermediate folders and test runners, then write that stale hierarchy back to disk. Never run `wally install` on its own.

After installation with Studio open, verify all seven `_Index/<package>/<name>` roots are `ModuleScript` instances and `ServerStorage.ServerPackages` exists before starting Play. The bundled Promise development runners (`runTests` and `modules.testez.test.runner`) must not exist in the installed runtime. Restart Play after synchronization and check both client and server startup; a passing disk analysis does not establish that Studio imported the same hierarchy.

## Ownership boundaries

- The server is authoritative for persistent state, economy, purchases, inventory, plot and building mutations, customer simulation outcomes, and rewards. Client handlers present that state and send requests.
- Shared modules must not depend on client-only or server-only modules. Runtime-specific behavior belongs in `ReplicatedStorage/Handlers` or `ServerScriptService/Handlers`.
- `ReplicatedStorage/Shared/Configs` owns static tuning and registries. Do not duplicate those tables inside handlers. Registry entry types are declared as an authored `Definition` plus the `id` that `Registry.Build` stamps on every entry. A registry's custom methods are typed by an explicit `<Name>Methods` table type, and the registry type is `Registry.Registry<Entry> & <Name>Methods`; annotating `self` with `typeof()` of the built registry is circular and leaves `self` untyped. Instance paths in configs are relative to the package root described under "Authored assets".
- `ReplicatedStorage/Shared/Bus.luau` defines the shared Packet cross-network contracts. The owning server handler validates requests and performs mutations; `Shared/Libs/Signal` supplies in-process events.
- Crystal owns handler startup order through each handler's `dependencies` and `priority`. A handler must declare the handlers it requires instead of reaching into another handler before `Crystal.Run()` finishes.
- Crystal completes all `OnInit` callbacks before running `OnStart` callbacks, with each phase ordered by dependencies and then priority among ready handlers. Startup callbacks are awaited. Dependencies use registered names, including `DataClient` for `DataHandlerClient`; nested support modules do not auto-register.
- `DataHandler` exposes Cloud/Session metatable proxies that track and replicate writes. Mutate through those proxies and use `Shared/DataList` for lists; raw table operations or writes to original tables bypass this contract. Every `Bus.Data.Update` carries the per-player `Revision` declared in its schema (Packet serializes declared keys only); the client ignores an update that is not newer than the last one it applied. `PurchaseHandler` is the sole receipt callback owner and preserves durable deduplication. Gamepasses never reach `ProcessReceipt`: `PurchaseHandler` grants them from the server-side `PromptGamePassPurchaseFinished`, and the server `StoreHandler` appends the pass to `Cloud.Passes` directly because `UserOwnsGamePassAsync` caches its answer per server.
- Product ids in `Configs/Registries/Products` belong to experience `10590744768` (owned by group `712136202`). Prices and sale state live on the Creator Dashboard only: the client `StoreHandler` reads `PriceInRobux` and `IsForSale` once per session, shows unpriced or off-sale products as a grey "Off sale" plate that does not prompt, and greys owned passes as "Owned". Roblox grants a newly created pass to the account that created it.
- Third-party code under `ReplicatedStorage/Packages`, `ServerStorage/ServerPackages`, and the vendored `Shared/Libs` entries above is not application code: fix call sites, not the libraries.
- First-party direct diagnostics use ordinary `print` instead of `warn`, preserving message content and control flow. Existing Logger levels remain available; its warning-level console output already uses `print`. Generated and vendored diagnostics are unchanged.

`HandsHandler` routes all seven carried item kinds through `FoodPreview.ShowItem`, including firewood through `CarryModel` and leftovers independently of recipe lookup. Tools use the configured `HeldAsset` (including `AnimationBroom`), or its furniture asset. Every preview uses the existing authored viewport template, normalized bounds and owned camera/cleanup; clearing a hand also clears its image. The hotbar label remains below the model.

`ToolReturnHandler` (client) guides every carried rack tool home: any building kind with a `ToolId` (broom, watering can, and hay once a hay rack is placed). While the replicated hands hold that tool, it clones the look of the player's rack (the authored `WorldModel`, else the furniture under the invisible prompt block, else the block) into a local copy under a white outline-only `Highlight`; the server's `SetCarried` hides the original. The engine skips Highlights on ordinary transparent parts but still draws them on glass, so the copy is stripped of textures and made `Glass` at 0.99 transparency (`Configs/ToolReturn`): only the outline shows. `Shared/UI/HintBeam` draws the arrow beam from the player to the copy every frame, through the doorway first when the rack is in another room (`Shared/UI/HintRoute`). While `TutorialHandler.Guiding` is set (the tutorial or its coaching shows any goal and is not collapsed), the beam is hidden so it never competes with the tutorial's own beam, and the outline only shows when that goal targets this tool (`TutorialHandler.TargetId`), so picking up the broom does not light the rack as the next destination. Releasing the tool destroys the copy.

## Analytics

`AnalyticsHandler` (server) reports to the Creator Dashboard by observing other handlers' signals; it never gates gameplay, rewards or saves. Studio never sends events: set `Configs/Analytics.PrintInStudio` (off by default) to print each one through the handler's logger instead. Live failures are caught and logged. Event names, funnel steps and day buckets live in `Configs/Analytics` and become dashboard keys, so keep them stable once live.

- **Economy.** `EconomyHandler.AddCash` / `TrySpend` take a `CashReason` (`Gameplay`, `TimedReward`, `IAP`, `Shop`, `Admin`) and an item id, and fire `CashChanged` with the amount that actually moved (pass multipliers included) and the new balance. Sales report the recipe id (through `DayCycleHandler.AddResult`), cat adoptions `CatAdoption`, rewards their track (`Code`, `Daily`, `Playtime`, and `PlaytimeSkip` reported as `IAP` because it is bought with Robux), cash packs the product id and upgrades the upgrade id. `Admin` changes, including `SetAdminCash`, are never reported.
- **Funnels.** `Day` runs once per in-game day: `Prep`, `Opened`, `FirstSale`, `Closed`, `NextDay`; a player who joins mid-day starts at their first step. `Store` runs once per purchase prompt (`PurchaseHandler.PurchasePrompted` then `PurchaseCompleted`), with the product id in the first custom field. The introduction keeps its onboarding funnel in `TutorialHandler/Analytics`.
- **Progression.** `Level` completes the previous level on every level up; `Day` completes the day number when its shift ends.
- **Custom events.** At each shift end, `ShiftCoins`, `ShiftServed` and `ShiftLost` carry the day's totals. Binning burnt food or an unwanted dish logs `DishBurnt` / `DishWasted`. Custom fields only carry the coarse day bucket or a product id.

## Kitchen ingredient sources

`BuildingHandler/OvenView` closes the authored oven leaves by aligning their local Z width with the line between their fixed hinges. Local X is mesh thickness and is excluded from the angle calculation: the offset between the hinge and bounding-box center previously added about 6.7 degrees of inward rotation to each leaf. Closed leaves now share one plane; their authored open pivots, client tween, cooking-state timing and teardown behavior remain unchanged.

`BuildingHandler/OvenDial` adds a depth-tested SurfaceGui over the inner clock face, behind the authored hand. `OvenView` shows its colored left semicircle only in `Ready` and `Burnt`, and rotates the hand through a full revolution during both baking and the ready-to-burn interval. `Configs/OvenMotion.Dial` owns mesh-relative placement, polygon shape, colors and marks; the generated overlay is owned by the oven's Janitor. Fuel exhaustion pauses the hand through the existing `HeatPausedAt` station state. Collection/reset hides the colored scale. The final red mark is rasterized from a polygon following the visible original contour and meets the twelve-o'clock seam; it is not a separate small capsule.

Oven timing follows the installed Lemon Cake build 6596857: all 30 oven recipe bake durations already match `DAT_Recipe.BakeTime` (5–30 seconds); their ready-to-burn interval is 30 seconds, or 60 with `kitchen_burnguard`. The first tutorial bake uses the same 30-second minimum. Fuel remains 90 seconds, or 180 with `kitchen_fuel`, plus a fresh random variation of -10 to +10 seconds. Evidence: `BP_KitchenOven` assigns recipe bake time at bytecode offset 2144, checks the combined bake/burn deadline at 4276, switches to a full burn-time clock revolution and shows `ClockBurn` at 7849, and randomizes fuel at 7097; `WBP_ShopSingle` assigns upgraded burn/fuel durations at 6180/12168. The original `SM_ClockBurn` and `TEX_ClockBurn` supply the left-half layout: gold from 180–270 degrees, orange to approximately 340 degrees, then dark brown with a red burn mark. Roblox uses flat GUI fills and simple marks adapted from those assets; the painted boundary and colors are visual estimates, not recovered gameplay thresholds. Source inspection and geometry checks do not replace an in-game visual test.

`FoodSurfaceView` continuously passes the server-owned ready/burn phase to `FoodModel:SetBurn`, including `HeatPausedAt` and the simulation time used during the day summary. `Shared/FoodBurn` reproduces `BP_Item.MaterialBurn`'s cubic zero-tangent curve: unchanged through 15/30 of the interval, smoothstep to full burn color at 28/30, then hold until the deadline. The upgrade stretches the same curve to 60 seconds. Food retains its texture instead of switching to a flat brown material. `FoodBurnHandler` owns client texture copies for tagged food parts, caches a palette per source color map, processes one image job at a time in roughly 3 ms CPU slices across frames, and restores/destroys materials on removal. PlayerGui viewport food parts also participate in burn rendering and bypass world-camera distance culling. Burnt previews receive an immediate approximate tint while their exact texture copy loads; cleanup restores the original tint. Authored templates outside the local PlayerGui remain untracked. `Configs/FoodTextures` records the color-map URI for each of the 44 recipe/dough meshes, exported from the authored Studio assets; runtime code reads this manifest because both `SurfaceAppearance.ColorMap` and `ColorMapContent` require plugin security. Update the manifest when those authored maps change. Unchanged and fuel-paused fractions do not redraw. The ready-to-burn transition retains the same model/material to avoid flashing a fresh texture. Completed burnt items receive the final fraction as well; existing recipe geometry and inventory identifiers remain unchanged.

Color evidence comes from the actual compiled `MASTER_FoodFade` pixel shader, not the unused `ColorBurn` material-instance overrides: the zlib stream at byte 2778 of its exported `Extras` contains DXBC (offset 92), decoded using Windows `D3DDisassemble`. In linear RGB, each channel uses `overlay(c,k) = c*k` below 0.5, otherwise `1-(1-c)*(2-k)`, with `k=(0.427084,0.176358,0.129414)`. It blends 10% toward the scalar dot product with `(0.141452,0.145833,0.046637)`, then interpolates from the source color by `Fade`. Roblox texture bytes are converted from/to sRGB around this calculation. This is the recovered color operation and timing, not a claim of identical engine rendering: the dynamic color copy is capped at 512 pixels, uses Roblox lighting rather than Unreal's unlit exposure pipeline, and retains the current Roblox food meshes. The original PBR maps stay on the retained authored appearance and are restored on teardown; the dynamic appearance carries the color result only. If editable-image allocation or source access fails, the client logs the reason once per item and uses an explicitly approximate tint fallback. A local Play audit confirmed viewport tracking, immediate tint, fallback completion and cleanup. This Studio experience currently rejects editable-image access until the API is enabled in Experience Settings > Security, so exact texture rendering still requires that setting and a new Play check.

Manual table and floor cleaning use `ServerScriptService/CleaningAction`, an explicitly required helper owned by the target building/floor Janitor. After the normal server validation, it rejects overlapping movement locks, fixes the character root in place facing the target, and uses `PlayerHandler`'s keyed movement lock to disable walking, jumping and automatic rotation. Both supplied cleaning clips are one second; `CharacterAnimations.Actions` owns that duration and does not cancel them for held movement input. Cleanup after the clip plus its fade, death, character removal or target teardown releases the root and only this action's lock. A failed table dispatch releases immediately. Assistant cleaning does not lock or animate the player. Existing successful-clean state changes and tutorial events remain immediate. Floor sweeping additionally uses `ServerScriptService/SweepPlacement`: a six-stud prompt/server reach, a bounded adjustment to 0.65 studs outside the rotated puddle footprint, and floor/path/torso clearance checks before accepting the action. Invalid or blocked placement leaves the spill untouched. `DayCycle.Sweep` owns these distances; table cleaning retains its existing position.

The garden sink and watering can are starter fixtures. `PlotHandler` prepares the existing `Garden.Upgrades.CrystalWater.Upgrade.Part` through its private `BuildingHandler/SinkWater` helper, giving it a translucent water surface and owned ambient droplets. `Configs/Garden.SinkWater` contains the authored path and presentation tuning. Both occupied and vacant bakeries retain this water; `UpgradeViewHandler` does not gate it on `garden_water`, and `VacantView` excludes it from upgrade hiding. The existing Crystal Water stat still doubles plant moisture duration. This follows installed Lemon Cake build 6596857: `LVL_Game.BP_Counter_6` starts with `WateringCan`, the independent `PS_WaterTricle_2` emitter runs at two droplets per second with a 0.75-second lifetime, and `WBP_ShopSingle.UnlockCrystalWater` sets plant dry rate to 0.5. The translucent Roblox basin surface, texture and dimensions are an adaptation, not recovered original rendering. These presentation changes are prepared from disk-backed source at startup and need no place-only asset edits.

Garden harvest prompts show the ingredient name without a stock/capacity counter. Availability still follows the server-owned stock.

Animal brushing chooses the nearest authored cow/chicken body in the source's care variant, rather than the first mesh in a flock. ## Success feedback

Every accepted success is presented, never decided, on the client; `Configs/Feedback` owns all of its tuning.

- **Dish sales.** `CustomerHandler.PayForDish` measures what actually reached the wallet (pass multipliers included; nothing once the shift has closed) and fires `CustomerHandler.DishSold` with a grade: table service maps the existing `VFXRules.Reaction` (`Happy` → `Perfect`, `Singing` → `Great`, `Angry` → `Late`; the protected tutorial guest is always `Perfect`), window purchases are `Sold`. The grade is decided before the coins so the service streak can pay: see **Service streak** below. `CustomerViewHandler.Sell` fires the grade's `Configs/VFX` burst at the guest's plate (`FoodSurfaceView` frame; window shoppers burst below the head) for every nearby player, and sends the owner `Bus.Cafe.Sale` (amount, streak tip bonus, grade, streak, new-record flag, guest head, sale position, cash after the credit).
- **The owner's view.** The client `FeedbackHandler` plays the register (pitch rising with the streak; a `Sparkle` flourish for `Perfect`), floats a billboard over the guest (`Popup`: grade caption, the HUD coin with `+N$`, the streak line `xN STREAK +P% TIPS` from two consecutive good sales, and `NEW RECORD!`), and launches 3–12 coins (`CoinFlight`) from the sale's screen point into the HUD coin `Currency.Main.Icon`; off-screen sales launch from the screen edge in their direction. Each landing ticks `Coin` one step higher and punches the icon. `Shared/UI/Stores/Wallet` holds back the part of a sale that the replicated cash already contains but no coin has delivered, and `Components/Hud` shows `cash - Wallet.Hold(cash)`, so the counter climbs as coins land. Each sale records the reported cash, so the counter never dips whichever of the data update and the sale arrives first, and a sale releases itself after `Coins.HoldSeconds`. Sales while a page covers the HUD skip the flight.
- **Service streak.** `Session.Streak` counts consecutive well-timed table sales in the running shift: `Perfect` and `Great` extend it, a `Late` dish or a seated guest leaving unserved ends it (`CustomerHandler.BreakStreak`, which sends `Bus.Cafe.StreakLost` with the lost length), window purchases (`Sold`) leave it alone, and `ClearCustomers` resets it quietly when a shift starts or ends. It is real money: a sale that keeps the streak raises its tip (never the dish price) by `Economy.StreakTipBonusPerStep` (10%) per earlier good sale, up to `StreakTipBonusMax` (+100%), through `Tips.GetSaleValue`'s `streakBonus`. `CustomerHandler.AdvanceStreak` also keeps the day's best in the new `BestStreak` report row (`DayCycleHandler:RecordBest`) and the all-time best in `Cloud.Stats.BestStreak` (added by `Reconcile`; a progress reset clears it); the first sale of a run that beats the record from `Streak.RecordFrom` (3) on is flagged as a new record. Milestones (3, 5, 10, 15, 20, 25, 30, then every 10) play `StreakMilestone` and `FireWhoosh`, show `StreakBanner` (a flame beside bare fire-gradient lettering `HOT STREAK!` / `ON FIRE!` / `BLAZING!` / `UNSTOPPABLE!` / `LEGENDARY!` under a heavy outline, no plate behind it; the run and its tip bonus in white-to-beige so it reads over the warm wood; fire confetti; it waits for a level-up banner that is still up) and fire a `StreakBurst` ring of the oven's flipbook fire at the character's feet. `ReportHandler` adds rows the screen was not drawn with by cloning the authored row named by `Configs/DayReport` `Template`.
- **Level ups.** `Bus.Day.LevelUp` now shows `FeedbackHandler`'s non-interactive banner instead of a status toast: rotating rays (the Store shine `80513051336918`), a generated gold star with the level, a lettered `LEVEL UP!` title (gold gradient under a heavy outline, no plate behind it), the recipes the level unlocks, screen confetti, the `LevelUp` fanfare and a `LevelUp` burst around the local character. ## Guest movement

The first admission of each shift is due after `DayCycle.FirstSpawnDelay` (0.5 seconds), prefers a seated guest, and reuses an available unowned pedestrian at the bakery porch without waiting for the street walk or its minimum age. If the friend list is still loading, opening demand allows a generated avatar. The guest then follows the ordinary doorway-to-chair route and chooses an order in `Orders.FirstGuestChooseSeconds` (one second); the protected tutorial guest instead waits for the player's `Take order`. Failed admissions retain opening priority until a body is reserved; tutorial stage gates and table reservations still apply. Later guests retain normal street admission and choosing times: arrivals every `DayCycle.SpawnInterval` (6 seconds, shorter than Lemon Cake's 10) times the display-flow multiplier, and `Orders.ChooseMinSeconds`–`ChooseMaxSeconds` (4–8 seconds) at the table. Once the introduction no longer gates arrivals, a bakery with no guests at all brings its next arrival forward to `DayCycle.EmptySpawnDelay` (1.5 seconds), so the room never sits empty for a full interval. `CustomerHandler.ReleaseTutorial` also owes `DayCycle.TutorialRushGuests` (2) arrivals `RushSpawnInterval` (2 seconds) apart, so the player has work the moment the introduction ends. Rush guests, like the shift's first guest and any guest arriving to an empty bakery, take the porch admission and choose in `Orders.FirstGuestChooseSeconds`. Owned guests walk at `Guests.CafeWalkSpeed` (11 studs per second); the street crowd keeps `WalkSpeed`.

`GuestOrderHandler` floats a speech bubble (`GuestOrderHandler/Bubble`) over each of the local player's seated guests while `Queued`, `Choosing` or `Waiting` (`Orders.Bubble.States`), mirrored from `Session.Customers` and resolved by customer id inside the owner's bakery `Guests` folder; other bakeries' guests get none. The bubble shows the ordered dishes through `FoodPreview` with their names, the seat number badge shared with the order cards (`OrderHandler.SeatLabel`), and the patience left on a clone of the order HUD's bar. Choosing guests show animated dots, queued guests `Need a table!`. New caption words type out letter by letter with the guest's positional `NpcText` blip at the head (`Orders.Bubble.Voice`), BattlesOfEmpires' NPC voice. The bubble pops in, punches when the order is placed, and below `Orders.Bubble.LowPatience` its bar turns red and it wobbles. It lives under `PlayerGui` with the guest's head as `Adornee`, because a `ViewportFrame` inside a `BillboardGui` parented in the Workspace draws nothing, and it uses `Sibling` ZIndex ordering, because the bar's `CanvasGroup` draws nothing under `Global`; and it is not `AlwaysOnTop`, because such billboards draw neither the dish `ViewportFrame` nor the bar's `CanvasGroup`; it has a `MaxDistance`, and it disappears when the guest starts eating, where the dining progress card takes over.

The `cafe_window` upgrade grants `WindowSlots` and rebuilds the kitchen window as Lemon Cake's `BP_Counter9` (`IsWindowCounter`): the `Window` building kind is a one-dish `DisplaySlot` dressed onto the authored `Cafe.Upgrades.KitchenWindow` mesh, with its food on the sill (`SurfaceOffset`) and its prompt reachable from the kitchen and the café. It keeps `Session.Window` / `WindowLeftovers`, uses `Bus.Cafe.WindowPlace` / `WindowTake`, and ages overnight like the display. Guests never buy from it; before its daily task, the assistant carries the window dish to a free display. The upgrade no longer raises `TipMult`, which the original never did.

A seated guest without a free, clean chair does not wait for a table. Following Lemon Cake `BP_Client.FindTable`, the guest becomes a roaming visitor even when no display is bought. `ClientRoam` walks to random points of the shop for 5-15 seconds; `StopRoam` then looks for a cat or a stocked display, and otherwise calls `LeaveShop`. Roaming visitors use the display flow on top of the pedestal browsers (`DisplayCustomers.RoamGuests`). Without a pedestal of their own, they walk between random points of the café runner (`CarpetRoute.RandomPoint`), at least `RoamDoorClearance` from the entrance. The original's random point in the shop's bounding box is adapted here to the runner, the room's authored walkway. A visitor who finds no stock leaves without a patience or streak penalty, as before. The `display_empty` notice (the original's `NoDisplayPastry`) is only sent to bakeries that own pedestals. The table queue now serves only the protected introduction guest: it stands inside, along the wall beside the entrance lane. `SeatQueue` seats queued guests in arrival order, restarts their patience for the walk to the chair, and moves the rest of the line forward through `CustomerHandler.QueueMoved`.

Every display guest holds its own window pedestal in `DisplaySlot` from spawn until it leaves or goes to adopt a cat; `Spots` routes browsing, roaming, and buying to that pedestal, so window shoppers never stack. A buyer prefers the stocked pedestal it already stands at, skips pedestals other buyers have claimed, and waits while every stocked pedestal is claimed; a browser on the chosen pedestal moves to a free one. Display guests never outnumber pedestals, so a free one always exists.

`CustomerViewHandler` marks eating guests with `Configs/GuestDining` timestamps and a tag using the server-owned `EatEndsAt`. Only explicitly listed handheld recipes receive a held-food attribute; other meals stay on their plate. `BuildingHandler/FoodSurfaceView` replaces the exact guest's held dish with its clean plate, preserving the other seat and dirty-plate lifecycle. `GuestDiningHandler` samples the right arm from the supplied eating animation (`74582433457576`), imported as the authored `ReplicatedStorage.Assets.Animations.EatHand` sequence. Its existing `JointPose` layer preserves seated legs and restores joint transforms before Animator evaluation. Local held food follows that hand; `Clearance` retains the accessory-aware rendered-food correction.

Private `PlateMotion` clones the authored `ReplicatedStorage.Assets.Models.Cutlery.Fork` and `Knife`: the right hand lifts the fork to the mouth during a 3.2-second cycle, while the left hand cuts near the plate and rests during the bite. Tags support late arrivals; the view retries missing streamed joints or templates and owns all pose, utensil, food, and billboard cleanup. The cutlery was authored in Blender and uploaded through `AssetService:CreateAssetAsync` to the experience's owner, group `712136202`. Cutlery templates and imported animation sequences are place-only content and must be saved with the place separately from Script Sync source.

`CustomerViewHandler/Guest` moves every street pedestrian and cafe guest on the shared 10 Hz tick. Humanoid `AutoRotate` stays off: an owned `AlignOrientation` turns the body toward a heading that rotates at most `Configs/Guests.TurnRate` degrees per second, so physics rounds each tick's heading step instead of snapping. The heading aims `LookAhead` studs further along the route and legs hand over at each corner's bisector, so corners become short arcs; `Humanoid:Move` walks along the heading. Pace eases with `Acceleration` and `Deceleration`, drops while the body faces away from its path (turn first, then stride), and on routes with a look-at target slows over the final `SlowdownDistance` studs before the guest stops and turns to face it. Routes without a look-at keep their pace, so a route started from the arrival callback continues without a stop. `Street` spaces the crowd through the guest's `SpeedLimit` rather than writing `WalkSpeed`.

Walk playback follows the guest's pace against `Avatar.WalkReferenceSpeed`; 9 studs per second keeps planted feet still on a default R15 rig. Idle, walk, and sit crossfade over `Avatar.AnimationFadeTime`. A seating guest first turns to the chair's facing at the normal turn rate, so the seat tween lowers the body instead of spinning it. The seated state is enabled in the same frame as the explicit sit, so Roblox's touch-to-sit cannot apply its default weld pose first. The facing constraint is disabled while the weld owns the pose; standing up hands orientation back from the body's current facing.

The title types out letter by letter with the `TextSay` voice (one sound restarted on each letter, as in BattlesOfEmpires; `Dialog.Voice.Sound = nil` types silently), and the player's own replies (Got it, a tap that finishes the line) answer with `ResponseText`; `{word}` in copy is drawn in the emphasis colour, a tap on the bubble finishes the typing, and every new line makes the bubble swell and hop like Lemon Cake's `AN_DialogueChange`. The goal's dish, tool or ingredient shows in a tile through `FoodPreview`. The bubble stays up for as long as its step is active, moves below the clock when it would cover its own GUI target, keeps each step readable for `MinShowSeconds`, plays a `Done!` stamp before a finished action step hands over, and survives goal-less frames for `HideGrace`. Read-only steps listed in `Dialog.Acknowledge` get a button (`order_card` shows `Got it`). Post-introduction coaching keeps the short status toast, which waits for current feedback to finish. All sizes, colours and timings live in `Configs/Tutorial.Dialog`. The saved collapsed preference still suppresses guidance; server-owned progress and existing debug controls remain. The introduction is enabled without resetting completed/skipped saves. Harvest guidance distinguishes animal care from kitchen output, and evening guidance uses the shared `BakeryMenu` header.

The introduction follows `Sweep → Cook → Serve → Clean`. `CleaningHandler:PrepareTutorial` prepares one authored spill only after the player's bakery is ready, at `Configs/Tutorial.SpillOffset` in the kitchen floor's local space (beside the walk from the broom rack to the mixer; a blocked spot falls back to a random one), and the spill glows (`goal.highlight`) while the player is asked to sweep it. The return step only follows an accepted sweep (`Actions.Mopped`); a broom taken before the spill appeared waits. The server waits for accepted mopping, no remaining spills, and the returned broom before cooking guidance begins. `PreparedFloor` is an additive action flag; existing cooking milestones and completed/skipped profiles are preserved without a version reset. Restarting with a selected recipe or a live batch bypasses this opening task; that is judged once, when the bakery is first ready (`Run.SweepJudged`), so choosing a recipe during the sweep no longer skips it. A bakery without authored spills can continue cooking, and the server logs that skip. Guests are held during `Sweep`, even if the player opens early. While the introduction runs, the mixer menu offers only its dish (`RecipePickHandler` filters to `TutorialPolicy.Recipe`, and `BuildingHandler.SelectRecipe` refuses any other), and the HUD shows each part only once the player needs it: the side buttons in `Configs/Tutorial.HudDuringIntro` (the shop) from the start, the balance from the `Serve` stage (just before the first sale), the clock when the player is asked to open (and from then on), and the other side buttons, the level bar and the topbar icons (`TopbarHandler:SetVisible`) when the introduction ends. `Shared/UI/Stores/HudReveal` holds one flag per group; `HydrateHud` slides a group in from its own edge with the same Ripple spring it uses for pages only while it is revealed, and holds every group's first entrance until the tutorial's first decision (`HudReveal.Ready`, or after 5 seconds), so nothing rides in at spawn just to ride back out. New side buttons join while the column is off screen (`HudSideSwapSeconds`). Ordinary cooking spills remain suppressed until the introduction ends.

World guidance uses the existing Beam until the exact target's actionable prompt is visible; then the finger points at its tappable plate without dimming the world. Another prop's prompt cannot replace the target. Waiting for mixing, baking, arrivals, or eating hides the pressing finger; the first order card stays spotlighted, with `OrderFocusPadding` extra room, until the player taps it (`OrderHandler.Tapped`) or presses the bubble's `Got it`, both remembered client-side by `TutorialHandler.OrderSeen`; only a gamepad (`TutorialContext.gamepad`) also moves on after `OrderPreviewSeconds` (20). The tutorial guest never orders on its own: `GuestState` skips the choosing timer while `TutorialProtected` is set, so `Take order` is the player's action, and the timer resumes once the tutorial releases the guest. Coaching toasts settle for 0.25 seconds to avoid intermediate replication messages and repeat after 18 seconds without replacing an active toast; both intervals are configured in `Configs/Tutorial`.

`State.FreeHands` never asks the player to clear a dispenser ingredient: `CarryPolicy.CanReplace` items return to their source on the next pickup, so the hand counts as free. Tools return to their rack, dishes and leftovers go to an empty display slot, dough goes to an idle station of its recipe, logs go to the oven, and burnt food goes to the trash. Only the introduction may send another item to the trash as a last resort, titled with the item's name; optional lessons wait while the hand holds anything else. Lemon Cake's own tutorial has no trash step.

After the introduction, optional lessons stay contextual and keep their bubble up while they apply. The floor lesson asks to sweep while any spill remains and only then to return the broom. The display lesson ignores a dish that any table guest still has to receive, including one who is still arriving or choosing. The garden lesson only runs during the untimed `Prep` phase, or while the player already carries the watering can; it never shows a waiting (growing) goal, so it cannot silence the coach and the tool-return beam all morning, and the first accepted harvest retires it (`Run.Action` sets `Lessons.Garden`). The cart lesson has two moments. `cart_load` appears only while the player stands in the garden (`HintRoute.Room`, passed in `TutorialContext.room`) holding produce grown there; milk and eggs come out of kitchen baskets (`OutputPath`) and never count. The first accepted `LoadCart` marks `Actions.LoadedCart`; after that `cart_take` points at the rail output only once a delivery has arrived and the hand is free, and the first `TakeCart` completes the lesson. A player who saw `cart_load` and then carries garden produce into another room by hand gets the `Cart` topic dismissed (`Lessons.CarriedPastCart`, sent once by the client `TutorialHandler`). When a page opens that the current goal does not target, `Presenter` hides its own status toast through `UIHandler:ClearToast` and announces the goal again after the page closes; other toasts are unaffected.

After the introduction, `Shared/Tutorial/Coach` (owned by the client `TutorialHandler`, presented through the same `Presenter`) helps a player who stops making progress or repeats a misunderstood refusal. `Shared/Tutorial/Assist` resolves the next useful step from live kitchen data, reusing `Cooking.Resolve`. It covers urgent guests and ovens, a dead oven fire, finished or burnt batches, used places, spills, quiet moments and the evening plan. The first days after the introduction (`Coach.Experience`, by `Cloud.Day`) wait less and point more often. The coach first shows a short cause-and-fix toast without a pointer, then points only if the player still has not acted. Delays, the refusal set, the nudge cooldown and the per-step pointer cap live in `Configs/Tutorial.Coach`. Repeated `Progress.ActionFailed` misunderstandings skip the wait. Bought features in `Configs/Tutorial.Features` that stay unused through a whole shift become due through additive `Use:`/`Due:`/`Feature:` flags written by the server tutorial `Run` on `DayCycleHandler.ShiftStarted`/`ShiftEnded` and accepted actions. The client `Shared/Tutorial/Features` then explains each one once in the evening plan, the next preparation, and at its first useful moment in the next shift. A second unused shift retires the guide. Coaching keeps client memory only; it never grants progress. See [HINTS.md](HINTS.md#coaching-after-the-introduction).

`Shared/UI/Tutorial/GuestHighlight` gives the local player's protected tutorial guest a warm outline and translucent fill while `Arriving` or `Queued`. It resolves the session's exact `GuestId` inside the owned bakery's `Guests` folder; other players' guests and ordinary pedestrians are never selected. `TutorialHandler` owns cleanup and retries late model replication through its existing refresh callback. Seating, guest removal, collapsed guidance, or ending the introduction clears the highlight. Visual tuning lives in `Configs/Tutorial.GuestHighlight`; no server state or authored asset is changed.

`Shared/UI/StatusLayout` binds the authored status frame through `UI/App`. `Configs/Notifications` owns viewport breakpoints, padding, typography, and dimensions: at most 240 by 32 pixels on compact viewports, 360 by 48 on wide viewports. Decorative tag/lines are hidden. Layout responds to the screen's available size and keeps the toast at least `Notifications.ClockGap` (16 pixels) below the clock's resting bottom edge, converting between screen origins. Clock resizing and safe-area changes recompute the position without following its entrance or press animation. The existing toast animation, state and cleanup owner remain shared; no second notification system is created.

`hinttest` previews GUI/world guidance through the server-authorized Cmdr `TutorialDebug` group and the one-way `Bus.Hints.Debug` packet. `HintDebugHandler` owns the preview lifetime independently of the tutorial. `tutorialtest` aliases the existing progress-reset command; it changes tutorial progress, whereas `hinttest` does not. See [HINTS.md](HINTS.md) for the API, examples, commands and verification limits.

Occupied-table tutorial targets retain their exact seat frame when a dish model is present. Hint destruction clears visibility, bounds, and occlusion query state as well as releasing owned resources.

`HintAnimation` owns the manually stepped finger FSM, with named `Rest`, `Press`, `Hold`, and `Release` states and explicit next-state links in `Configs/Hint.FingerPhases`. Each hint composes this animation with its surface and beam; suppression pauses the animation, changing target identity resets it, and destruction releases it. Target resolution uses distinct GUI/world records. GUI focus, world projection/occlusion, and finger placement have separate functions with one shared frame context. `HintGeometry.Inset` owns safe-region shrinking, and ancestor visibility is checked by one flat predicate. The existing common render callback remains the sole scheduler; an ECS or a second handler loop is unnecessary for this fixed presentation pipeline.

Hint sizes, rotation limits, animation limits, shade color, occlusion thresholds, beam retry/texture limits, and tutorial/debug offsets live in `Configs/Hint`. Geometry tolerances remain named local constants. Cmdr preview modes use a typed dispatch table; presentation selection and lifetime cleanup have separate owners. Disabling occlusion or switching to GUI guidance clears the previous world-obstruction result.

## Developer panel

The developer panel uses English for labels, confirmations, status, and server responses.

`AdminPanelHandler` creates an owned developer overlay, opened with **F4**, **/admin**, or its **ADMIN** button. It does not replace authored `MainGui` screens. Player selection is limited to the current server; the panel supports status inspection, exact coin grants/balance replacement (without paid multipliers), XP, pantry stock, upgrade grants/budget, tutorial restart/skip, day transitions, hand cleanup, respawn, and full client data resynchronization. Actions call the existing owning handlers, preserving their signals, caches, state machines, and proxy writes.

Tutorial actions report a refusal while `Configs/Tutorial.Enabled` is false; the panel does not override the game's global tutorial switch. Day actions retain the existing phase/menu requirements and report refusals instead of forcing invalid state transitions.

`AdminHandler` authorizes every `Bus.Admin.Request` on the server. Published servers use the existing UserId allowlist in `ServerScriptService/Cmdr/Admin.luau` (currently `codebykoi` and `funseti`); add another developer's numeric UserId there and deploy the source change. Studio permits local test players. Roblox edit/collaboration permissions are not automatically treated as runtime admin access. The replicated `AdminPanelAccess` attribute controls presentation only and never authorizes a mutation.

Every panel mutation requires an expiring, one-use server confirmation bound to its executor, target Player instance, action, and amount. Requests validate finite integer quantities, action-specific limits, profile readiness, and pending resets; executor throttles and target locks prevent overlapping panel operations. Unknown actions and arbitrary data paths are rejected. The server Output records attempts/results with executor and target IDs; the panel exposes the last 30 results from this server's memory, not a durable cross-server audit service. Offline edits, bans, receipt grants, and arbitrary code execution are not exposed.

Progress reset uses `DataHandler:RequestProgressReset`: save the pending marker, end the session, and apply new-player defaults before `PlayerReady` on rejoin. It now starts with normal starter cash rather than an upgrade budget. Paid passes, skins, receipt deduplication, and `Stats.RobuxSpent` survive. The separate upgrade-budget action remains available. `DataHandler:ResendSnapshot` flushes preceding deltas and resends both stores using the existing snapshot/revision channel.

For isolated Studio QA, set the attribute `AdminTestMockData = true` on **ServerScriptService.Handlers.DataHandler** in Edit mode before starting Play, then remove it after stopping. `DataHandler` honors it only in Studio and uses ProfileStore.Mock; the configured live store and saving policy remain unchanged. The panel shows `STUDIO MOCK` when this mode is active. Ordinary Studio Play still saves real data when `StudioSavingEnabled` is true. Reset/rejoin persistence must be checked separately: a fresh Play session does not retain the in-memory mock store.

## Validation workflow

- `rokit.toml` pins Selene, StyLua, luau-lsp, Wally, and wally-package-types. Run tools through Rokit from the repository root.
- `scripts/check.ps1` is the verification gate: it regenerates the sourcemap, runs `selene .`, fails if any first-party `.lua`/`.luau` file does not start with `--!strict` (files matching `luau-lsp.ignoreGlobs`, the Wally packages and vendored libraries, are exempt), then runs the pinned analyzer over every source root: `luau-lsp analyze --platform roblox --definitions <globalTypes.PluginSecurity.d.luau> --sourcemap sourcemap.json --settings .vscode/settings.json ReplicatedFirst ReplicatedStorage ServerScriptService ServerStorage StarterCharacterScripts StarterPlayerScripts`. Definitions are resolved from `.zed/.cache` first, then the luau-lsp extension's Cursor/VS Code global storage; pass `-Definitions` to use another copy.
- Analysis uses luau-lsp's default type solver, matching the editor. Two shared shims exist because of it: `BaseStats.StatKey` is an explicit key union (no `keyof`), and `Shared/UI/Scope.luau` wraps `Flux.scope` for callbacks that return nothing. Flux selectors (`Find.Path`, `Find.Child`) are given plain signatures where they are used.
- Every first-party module is `--!strict`, so Studio's Script Analysis checks it strictly too. Three solver limits shape strict code here: a runtime-resolved `require` (Crystal's handler discovery, Cmdr's generated `CmdrClient`) is written `(require :: any)(module)` because strict mode rejects paths it cannot resolve; an instance built with `setmetatable` is only assignable to its own class type, so a field holding one uses that type (`Building.FoodVisual: FoodSurfaceView.FoodSurfaceView?`) instead of a structural interface; and reassigning a `T?` local inside `if not x then` does not narrow it afterwards, so use `existing or create()` or an early return.
- The editor runs Roblox's live FFlags while the CLI enables all stable flags, so the editor can be stricter about missing optional table fields. Config-style inputs therefore get their own input type (for example `StateMachine.StateDefinition`, the registry `Definition` types) rather than reusing the fully-populated runtime type.
- `.vscode/settings.json` and `selene.toml` exclude the Wally directories and the vendored libraries from diagnostics and lint. DataModel diagnostics use luau-lsp's default `strictDatamodelTypes = false`; the filesystem sourcemap cannot describe place-only assets such as `ReplicatedStorage.Assets`. Zed explicitly uses the same setting. This does not disable `--!strict` Luau checking; authored instances can be declared as an `AuthoredScreen`-style intersection type at the point of use.
- Formatting follows StyLua defaults; `.styluaignore` mirrors the lint exclusions. The `--[[ Section ]]--` header comments are rewritten by StyLua, so a repo-wide `stylua --check` is not part of the gate.
- The luau-lsp Studio companion plugin talks to the editor on port `3668` (`luau-lsp.studioPlugin.port`), shared with the other projects the Studio plugin is configured for, with `maximumRequestBodySize` raised to `50mb` because this place's DataModel dump exceeds the 3 MB default. Only one workspace can own the port at a time.

## Zed on Windows

Install Zed's `Luau` extension (`4teapo/zed-luau`), run `rokit install`, then `scripts/setup-zed.ps1`. The setup script caches Roblox PluginSecurity definitions and API docs in the ignored `.zed/.cache` directory and installs `4teapo/luau-lsp-proxy` v0.1.0 into the Luau extension's work directory. Use `-Refresh` to refresh these downloads. `scripts/check.ps1` can then run without VS Code or Cursor installed.

`.zed/settings.json` uses the Rokit `luau-lsp` and `stylua` commands from PATH, enables workspace diagnostics, and mirrors the project's vendor exclusions. DataModel diagnostics match VS Code and the CLI; enabling `strictDatamodelTypes` without a complete Studio tree reports missing place-only children. Zed uses stable CLI flags without live Roblox flag downloads or the experimental solver. StyLua runs on an explicit format command and respects `.styluaignore`; saving alone does not reformat existing section comments.

The Studio companion connects through the proxy on port `3668`. The proxy accepts compressed DataModel updates; the VS Code `maximumRequestBodySize` setting does not apply to it. Close the other editor's Luau workspace before using this port in Zed.

Use `task: spawn` for the project tasks in `.zed/tasks.json`: tool/package installation, Zed setup, the full check gate, and sourcemap generation. Zed's Luau extension does not run the VS Code sourcemap generator. After adding, removing, moving, or renaming scripts with Studio's Script Sync inactive, run `Regenerate sourcemap` (the check and package tasks also regenerate it). Source-content edits do not require regeneration. The generator and Selene exclude Zed's generated definitions from game source.
