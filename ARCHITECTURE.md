# Architecture

## Repository guidance

Repository content is English-only: documentation, memory notes, source comments, user-facing strings, tooling, and generated reports follow the mandatory [repository language rule](AGENTS.md#repository-language-mandatory). Generators must preserve this rule when rebuilding their output.

`AGENTS.md` is the shared session/startup and verification contract. `CODE_STYLE.md` defines Luau conventions for new and touched code; `PACKAGES.md` maps the actual dependencies and call-site boundaries. `CLAUDE.md` imports the shared rules, while `.github/copilot-instructions.md` directs Copilot to them and includes the core verification requirements. Cursor uses root `AGENTS.md` directly. Zed's filename precedence selects the Copilot entry here, which directs it to the shared rules. Keep these entry files thin instead of maintaining independent architecture copies.

Generated sourcemaps, installed Wally packages, logs, temporary files, editor backups, and operating-system metadata are excluded through `.gitignore`. Keep dependency manifests and lock files under version control.

Reference research lives in [Exeperience/LemonCake](Exeperience/LemonCake/README.md), with a short retrieval guide in [mem/lemon-cake.md](mem/lemon-cake.md). The Lemon Cake snapshot records Steam build identity, extracted data, Blueprint indexes, reproduction tools, and verification limits. Original extracted assets and full dumps stay in its ignored `.local` cache. These folders are documentation/research tooling, not Roblox runtime source roots; the reference does not override this project's architecture or adapted balance.

## Runtime layout

The repository mirrors Roblox DataModel services on disk. Studio's Script Sync keeps the place and this folder in step (scripts only; it maps directories literally, so a directory holding `init.luau` is that script with its siblings as children, and `.client` / `.server` / `.legacy` suffixes pick the script class). `.vscode/generate-sourcemap.ps1` applies the same rules to produce `sourcemap.json` for the Luau Language Server, so the gate works with Studio closed. Script Sync also writes its own `sourcemap.json` (absolute paths) whenever it syncs; the two are interchangeable for luau-lsp, and neither is edited by hand or committed.

`StarterCharacterScripts` and `StarterPlayerScripts` live at the repository root and are mapped under `StarterPlayer`.

- `ReplicatedStorage/Client.client.luau` is the client bootstrap. It loads `CmdrClient` when present, registers every direct child module of `ReplicatedStorage/Handlers` with Crystal, then calls `Crystal.Run()`.
- `ServerScriptService/Server.legacy.luau` is the server bootstrap. It registers Cmdr hooks, types, and commands from `ServerScriptService/Cmdr`, registers every direct child module of `ServerScriptService/Handlers` with Crystal, then calls `Crystal.Run()`.
- `ReplicatedStorage/Handlers` contains client handlers. `ServerScriptService/Handlers` contains server handlers. Crystal loads a handler only when it is a direct `ModuleScript` child of those folders; nested modules are required by their handler.
- `AmbientMotionHandler` loads shared clips from `ReplicatedStorage.Assets.Animations.Ambient`, skipping non-`KeyframeSequence` children and unreadable clips with loop guards. Missing clips do not prevent visual setup; a missing folder prints a diagnostic message.
- `ReplicatedStorage/Shared` contains code and data safe to require from either runtime: Crystal, the bus, configs, UI, shared gameplay views, and utility libraries.
- `ReplicatedStorage/Shared/Libs` holds `Logger` and `StateMachine` (project code) next to vendored third-party libraries: `Packet`, `PartCache`, `Ripple`, and `Signal`. The vendored ones are committed as-is and excluded from lint and type analysis.
- `ServerScriptService/Cmdr` contains Studio/admin command definitions. The client command surface is `ReplicatedStorage/CmdrClient`, created by Cmdr at runtime.

## Authored assets

Authored content ships as Roblox Packages (`PackageLink`) and lives in the place: `Workspace.World` (bakeries, environment, roofs, and spawn), `ReplicatedStorage.Assets` (prompt billboard, animations, model templates, source art, and VFX), and `StarterGui.MainGui` (every ScreenGui). These package roots add a wrapping folder, and code addresses the contents relative to it:

- `ReplicatedStorage/Shared/World.luau` is the only place that knows the world package's location. `World.Root` / `WaitForRoot` find `Workspace.World`; `World.Bakeries` and `World.Find(path)` resolve below it. Configs that name world content (`Base.BakeriesFolderName`, `Traffic.RoadPath`, `Traffic.Signals.Path`, `Guests.Street.SidewalkPath`) are child-name paths relative to that root, never to `Workspace`. Templates that are cloned rather than placed (building models, food, tools, traffic vehicles, and cats) live under `ReplicatedStorage.Assets.Models`. Anything else the game needs from the world must go through this module rather than `workspace:FindFirstChild`.
- `ReplicatedStorage.Assets.Models.Cats` contains the four original `cat` rigs. `CatHandler` reads the folder named by `Cats.TemplatesFolder` and keeps its existing MeshId sort, preserving saved variant indices. Its prepared runtime copies remain in `ServerStorage.CafeCatTemplates`; spawned cats belong to their bakery. The `Scratch` slot has no authored clip: the client pitches the body nose-up around the hind feet (`Cats.ScratchPitch`, `ScratchPivot`) so the front paws rest on the post, and the slot offset keeps the head clear of it.
- Cat length follows the installed Lemon Cake build 6596857 ratio to its cat tree: `SK_Cat` imported length 171.246643, multiplied by `BP_Cat.Cat` scale 0.85, divided by `SM_CatTree` height 173.489883 and `BP_CatCafe.SM_CatTree` scale 1.075. `SpawnCats` bytecode at offsets 886 and 1142 explicitly uses unit actor scale; the location marker's 0.5 X scale does not shrink the cat. The resulting `Cats.LengthToTreeHeight` is 0.780474, giving a 3.868-stud cat beside the authored 4.956-stud tree (previously 2.4). All slots use the tree as the common size reference. This matches relative length while preserving the supplied Roblox rig's proportions; poses and meshes differ from the original. Source packages are in the ignored reference extraction under `Exeperience/LemonCake/.local/json/Art/Mesh/Animal`, `Art/Mesh/Furniture` and `Blueprints/Shop`; `SK_Cat` bounds are seven little-endian floats after the two strip-flag bytes in its decoded `Extras`, consistent with [CUE4Parse skeletal-mesh deserialization](https://github.com/FabianFG/CUE4Parse/blob/master/CUE4Parse/UE4/Assets/Exports/SkeletalMesh/USkeletalMesh.cs).
- `ReplicatedStorage.Assets.SourceModels` preserves the remaining 105 artist originals formerly staged in `Workspace.World.Assets`, including duplicate names and the original cake folder. This reference-art collection is outside `Models` so `Buildings.FindAsset` cannot accidentally select an unprepared duplicate. Names, pivots, meshes, and existing prepared model paths are preserved. The embedded plant animation script is disabled in this collection (`SourceTemplateWasEnabled` records its previous state), so stored source art does not animate. Promote usable templates into the appropriate `Models` category deliberately. Asset reparenting and script enabled state are place changes; Script Sync does not serialize them, so save the edited place separately from the source commit.
- `UIHandler` waits for `PlayerGui.MainGui` (`SCREENS_FOLDER`) and hands that folder to `Shared/UI/App` as the root that all screens are looked up under. Nothing else looks up an authored screen by name in `PlayerGui`; drivers go through `UIHandler:GetPanel` / `GetHud`.
- `Shared/UI/TextScale` reads `Theme.TextScale`: a 1280 by 720 reference canvas with density clamped from 1 to 1.4. That page density never drops below 1, so always-visible screen UI (HUD, guidance, overlays) and pixel-sized world billboards (prompt plates, station labels) use `TextScale.Screen` instead, while billboards that label a guest keep a constant world size through `TextScale.World`: the same reference canvas under `Theme.ScreenScale`, clamped from 0.6 to 1 (callers that grow on large desktops pass a higher maximum). A phone landscape screen (about 852 by 393) therefore draws them at 0.6, so they cover roughly the share of the screen they cover on a desktop, while desktops at or above 1280 by 720 are unchanged. `Responsive` fits each logical page uniformly within both safe viewport axes with 16-pixel margins, combining that fit with the existing page spring. Safe areas shorter than 500 pixels (landscape phones, where pages are height-bound) keep 8-pixel margins above and below instead, the least that keeps the bakery header, which rises 22 logical pixels above its panel, clear of Roblox's topbar buttons. Page art is authored to that fit: the Upgrades body starts 8 logical pixels under the shared bakery header (y 42, like Report); both Playtime ribbon tails stick 40 logical pixels past the panel; the Cooking card's outlined background leaves 6 logical pixels inside its clipping scroll frame; and each recipe row's ingredient grid splits its strip into four square cells (`CellSize` a quarter of the width, a `UIAspectRatioConstraint` under the grid), 72 logical pixels wide and 64 in the compact layout. Pages keep their authored proportions on every screen: the fit is capped by `TextScale.Screen` (with the page maximum of 1.4) instead of the page density, so a short page such as Codes takes the same share of a phone screen as of a desktop. Text constraints retain their authored maximum in `AuthoredMaxTextSize`, so repeated viewport changes do not compound scaling. Only portrait viewports narrower than 700 pixels use the 360-pixel compact canvas (`CompactHeight` tall); every other viewport, phone landscape included, fits the desktop canvas (`PanelWidth` by `PanelHeight`) like a small window, so phone pages look like scaled desktop pages rather than reflowed or stretched ones. Authored `ShortSize` / `ShortPosition` overrides apply only to canvases shorter than 500 logical pixels (Codes); the short-layout code in `ReportHandler`, `MenuHandler` and `CardGrid` is idle for the current pages. Elements with only a Short or Keyboard override record their pre-override geometry in `AuthoredSize` / `AuthoredPosition` attributes and get it back when the override ends. `TextScale.Size` and `TextScale.Bound` apply a configured min/max text range at a density for generated labels (prompt plate, status strip, rare-guest banner); HUD labels (order cards, hotbar names, invite row) use `HudLayout.TextSize`, which also floors them at `Theme.ScreenScale.MinTextPixels` (10). `Theme.ScreenScale` owns the shared small-screen floors: rendered text no smaller than `Theme.ScreenScale.MinTextPixels` (10) pixels where a surface enforces it, and touch targets at least `Theme.ScreenScale.MinTouchPixels` (44) pixels on a side. `Configs/HudLayout` owns the HUD's compact switch (`CompactWidth`/`CompactHeight`, which only changes the arrangement), the density cap `MaxScale` (2) and `QuestPrice`, the runtime adaptation of the authored quest reward badge. `Shared/UI/HudLayout` draws every HUD group from one set of 720p logical sizes at `HudLayout.Scale` (`TextScale.Screen` of the HUD's safe-area size, capped at `MaxScale`), so phones (0.6) and tablets (about 0.8) keep roughly the desktop share of the screen; compact viewports only rearrange the quest panel and the clock: on a phone the clock (`Time`) leaves the top centre for the topbar row, 12 pixels past the last visible TopbarPlus icon in `TopbarStandard.Holders.Left` and level with it, as long as it fits before the right margin (an empty row, as during the introduction, or a portrait screen keeps it centred). `HudLayout.Bind` re-applies when that row moves or its content width changes. The currency plate (coins and the Friend Boost row) keeps the screen's left edge on every device, resting in the bottom-left corner. A screen too narrow for it beside the hotbar lifts it above the hotbar. Roblox's touch controls never move it (the movement stick may rest over it); only the order row and the XP toast move around them. The side-button column fits between the top edge and that corner, centred on the screen when it clears it; short screens shrink its buttons, never below 44 pixels. The clock keeps a 44-pixel height, and the quest arrow and XP plus hitbox 44 pixels.
- `PromptHandler` clones the place-authored `Assets.Prompt` and applies `Configs/Prompts` to the runtime copy. Actionable billboards use 180 by 64 reference pixels on wide viewports and 168 by 60 on compact or short viewports; status-only plates use 176 by 44. Reference pixels are multiplied by `TextScale.Screen` (1 on desktops at 1280 by 720 and above, about 0.8 on tablets, 0.6 on phones), except that a plate the player can press never drops below `Theme.ScreenScale.MinTouchPixels` (44) pixels tall, so a phone shows 123 by 44 action plates and 106 by 26 status plates. A status line is centred on its wooden sign in a box 0.8 of the plate wide and 0.5 high: inside this billboard scaled text fills its box and ignores its `UITextSizeConstraint` (measured: limits of 10 and 14 both rendered 36-pixel text), so the box sets the size, about 22 pixels at reference density (about 13 on phones). Prompt density never exceeds 1 and is independent of the shared page density, with 16-pixel viewport edge padding. Existing keyboard, touch and gamepad artwork uses 32 by 32 reference-pixel input badges, scaled with the plate. Wrapped name/action/status labels have a 12 reference-pixel minimum and respective 17/15/14 maxima. Owned camera, viewport and status listeners preserve the pixel size across distance and state changes. Existing input behavior, page suppression, stable world anchoring and animation remain owned by the same handler. These dimensions require no authored place mutation.

Its caption reads `Empty`, with both text layers horizontally centered inside the centered status container. Empty plates remain passive placeholders without a food viewport and continue toggling with the existing filled plates as recipes are selected.

Eight logical pixels above and below the list protect selection outlines from clipping. The recipe card and the mixer billboard share `Shared/UI/IngredientCard` for ingredient names, ordering, chips and the pantry-take press: the scrolling recipe card binds taps (`Press.BindTap`), the world billboard binds presses that leave the mouse to the camera. Returning to a taller viewport restores the full-height rows and clamps the scroll position. Captions and numbers have matching 20-pixel logical side insets and a reserved gap between their columns. It hides the old `Middle.Lines` dashed inset, which would otherwise draw over the first and last rows. Responsive attributes and text baselines preserve these layouts across viewport changes; canvas height is explicit rather than derived from scaled rows.

During `Summary`, the header shows the Report, Upgrades and Menu tabs and Next Day, so the evening can shop before planning tomorrow. - `ReplicatedStorage.Assets.VFX` holds one flat `BasePart` per effect named in `Configs/VFX.Effects` (plus `OvenFire`), carrying the emitters and the placement attributes `VFXHandler` reads (`SourceOffset`, `SourceFoodSize`, `SourceToolSize`, `BodyOffset`). These parts were extracted from the artists' staging rigs (the `SourcePath` attribute records where); the rigs themselves are not part of the place. Author a new effect by adding a part here and a row in `VFX.Effects`, never by shipping a rig; a burst composed from existing emitters can instead be described in `VFX.Procedural` (see "Success feedback").
- `StarterGui.ResetPlayerGuiOnSpawn` is `false` in the place. Every screen was already `ResetOnSpawn = false` and is bound once by the client, but a Folder in `StarterGui` has no such property: with the default setting Roblox destroys and re-copies the whole `MainGui` folder on respawn, which leaves the client holding dead screens. The place-level setting keeps `PlayerGui` intact across respawns. Do not turn it back on.
- `Players.CharacterAutoLoads` is `false` in the place, and every bakery's `Anchors.Spawn` is a hidden `SpawnLocation` (no collision, touch, query or force field, `Neutral`). `BaseHandler.LoadBase` sets the claimed bakery's pad as the owner's `RespawnLocation`, streams its surroundings (`Configs/Base.StreamTimeout`) and only then loads the first character, so a character never appears in the air at the default spawn and is never moved after spawning. Deaths respawn after `Players.RespawnTime` at the same pad; a player left without a bakery on a full server still spawns, on any bakery's pad. StarterGui reaches `PlayerGui` with that first character, so `UIHandler` waits for `MainGui` without a deadline, like its data wait. Turning auto-loading back on would spawn every character twice.
- `ReplicatedFirst/Loading` replaces Roblox's loading screen with the authored `ReplicatedFirst.LoadingScreen`: the generated bakery background and cake badge ([assets/ui](assets/ui/README.md)), a red ribbon, the game's yellow-to-orange striped bar and rotating tips. Its 1280 by 720 canvas is fitted uniformly to the screen. After `game.Loaded` it caches only the interface art (`Configs/Loading.Preload`, `MainGui`) in one `ContentProvider:PreloadAsync` call, so the engine fetches it in parallel and each finished asset advances the bar up to `AssetShare` (90%). Meanwhile it waits for the character and `MainGui`; once they arrive it waits at most `AssetGraceSeconds` (3) for art still downloading, holds at least `MinSeconds`, fills the bar and fades out. Models, effects, prompts and the `Configs/Sounds` effects (`Configs/Loading.Background`) are cached only after the screen lifts, so a first join on a new device is not a full download of the game. Image ids are preloaded as content strings; mesh, sound and animation ids go through their instance (one per unique id, with unparented `Sound` carriers for the effects), because `PreloadAsync` fetches a bare string as an image and warns "Asset type does not match requested type" for anything else. Skip appears after `SkipAfterSeconds` (6) and lifts the screen at once. It prints when the character arrived and when the screen lifted, for reading join times in the F9 console; Studio Play lifts after about 3.7 seconds. `Configs/Loading` owns the tips, statuses and timings.

`ShopHandler` preserves the authored upgrade-node stroke thickness during selection. Availability still determines node colors, while selection updates the footer and plays the existing press animation; selection does not replace the cream fill with white or thicken the border. All three category tabs use the Store/Kitchen background image so Greenhouse has the same thin border. `Configs/UpgradeTabs` is the one ordered list of Upgrades tabs (name and category), read by `ShopHandler` and the tutorial's `UpgradeLesson`. `Registries/Upgrades.ReadInputs` / `ReadProgress` read upgrade levels, player level and cash from replicated data for the HUD goal, the report, the shop and the HUD affordable count.

`Configs/Registries/Upgrades.GetPurchaseCost` resolves the next level using the existing maximum level, player level, parent/prerequisite and price rules. `GetProgress` derives the affordable count and recommends the cheapest unlocked next level, breaking equal-price ties by stable upgrade ID. Thus a recommendation is affordable whenever any upgrade is affordable. Presentation reads server-replicated Cloud cash, level and upgrade levels; wallet coin-flight animation does not determine affordability. `UpgradeHandler.TryBuy` uses the same eligibility method, spends through `EconomyHandler`, writes through the data proxy, invalidates its stat cache and notifies `StatsChanged`, then sends the owner `Bus.Progress.UpgradeBought(upgradeId, purchasedLevel, paidCost)`. Failed requests and admin grants do not send this purchase event. When the selected purchase is short of coins, the footer still shows the gold Purchase plate; pressing it (or the gamepad `UpgradesPurchase` X cue) sends no `BuyUpgrade`, and `ShopHandler.OfferCoins` calls `StoreHandler:BuyCoins(cost - cash)`, which prompts the smallest `Store.Currency` coin pack whose coins (after the owned-pass `Products:GetCashMultiplier`) cover the shortfall, or the largest pack when none does, skipping packs without a product id or off sale. It goes through `StoreHandler:Buy`, so the `Store` analytics funnel records it like a Store press. A server `not_enough_coins` refusal (the replicated balance lagged a spend) still toasts and also offers the pack for the selected node. `UpgradeHandler.TryBuy` still rejects any purchase the wallet cannot cover; the offer is remembered (`ShopHandler.Pending`, `PACK_WAIT` 120 seconds), so when the pack's coins land while Upgrades is still open the upgrade is bought at once; a cancelled prompt (`PromptProductPurchaseFinished` without a purchase) or leaving the page drops it. Short-of-coins nodes keep the buyable gold outline and full icon.

A tree with no unlocked purchase shows its blocking requirement; a finished tree shows completion and no purchase alert. The existing fold control, tutorial HUD reveal policy and modal hiding remain in effect. `UpgradeRevealHandler` presents only accepted `UpgradeBought` receipts, deduplicated by upgrade and purchase level. Its private `Target`, `Appearance`, `Camera`, and `Card` modules resolve the owner's actual bakery, fade newly purchased geometry locally, choose an unobstructed view, and show an owned cream receipt with the existing upgrade icon, a concrete benefit, and Skip. `Configs/UpgradeReveal` owns paths, timing, camera scoring, card layout/colours, category labels and per-level benefit text for all 27 upgrades / 33 purchase levels; the private `Metrics` module sizes the receipt for both `Card` and `Camera`, in logical pixels drawn at `TextScale.Screen` density (a UIScale on the receipt), with text floored at `Theme.ScreenScale.MinTextPixels` (10) rendered pixels. Fade masks are recaptured every `CaptureInterval`, the card lays out on viewport changes only, and `Finish` releases the page presentation before any other teardown. Destroying the Upgrades panel cancels the current reveal but keeps the handler running. Stat purchases feature the mixer, oven, animals, sink, kitchen window, or player without fading existing equipment. The rail cart focuses its loading structure; the sprinkler focuses its central ceiling junction. No new world model is invented for an upgrade that changes a stat.

The reveal normally lasts about 2.8 seconds, including replication settling and camera return. Camera framing accounts for object depth and reserves space above the receipt. Spherecasts and overlap queries validate endpoints and movement; a short veil covers a safe cut between rooms when a direct move crosses geometry. The veil and the input shield sit on their own full-device `UpgradeRevealCover` screen (`ScreenInsets.None`, one `DisplayOrder` below the receipt), so on phones they reach past the notch and status bar that the receipt's safe-area screen keeps clear of. For the same reason `Shared/UI/App` sets the authored `MainGui.Backdrop` (the page dim) to `ScreenInsets.None` at runtime; its authored `DeviceSafeInsets` left the notch and top edge undimmed. Orbiting stops before clipping or losing the reserved framing. A blocked view or an existing Scriptable camera uses the receipt without taking camera ownership. `Appearance` changes only local transparency; tagged ambient meshes pass the local alpha to `AmbientMotionHandler/Visual` so its animated copies fade too. ## Rendering cost

Roblox caches shadow maps for still world geometry. An anchored part that a script moves every frame, even one that casts no shadow, makes the cached shadows around it re-render every frame, sun cascades and shadowed point lights alike. Inside a bakery that cost about 550 extra shadow draw calls and 450,000 shadow triangles. Parts inside a `Humanoid` model render as dynamic objects, like characters, and leave the cache alone. Neither unanchoring a part nor an `AnimationController` model does this.

`Shared/DynamicRig` is the one place this rule lives. A rig is a client-local `Model` containing a `Humanoid` (state machine off, no name or health display) and an anchored, invisible `Root` placed at an origin frame. `Attach` hangs a part from the root on a kinematic `AnimationConstraint` at the part's current frame. `Place` moves the part to a world frame by writing only the joint's `Transform`. Every continuously animated world visual uses a rig:

- `AmbientMotionHandler/Visual` rigs each garden copy at its home frame. Bees and plants move through `Place`; bone clips (cows, chickens, bees) still write `Bone.Transform`.
- `TrafficHandler` rigs each car and places it along its path every frame.
- The place-only `FeuillesBalancement` Script (RunContext `Client`) in each of the 48 authored `Plant` models (`Cafe.Decoration`, `Garden.Decoration`) keeps the authored `Feuille` leaves still, with their collisions, and hides them locally. Local copies on a `LeafSway` rig inside the plant model sway with the original tuning: a 2.5° roll, a 2.2° pitch, a 0.1-stud bob, an azimuth phase lag, and a freeze beyond 300 studs. The 48 copies share one source and are edited through Studio, not on disk.

Measured in Studio Play with the authored lighting, these changes took the shadow pass from about 590 to 35 draw calls inside the cafe and from about 510 to 50 from the street. With all garden visuals shown, the garden view went from 558 to about 106. New script-driven motion of world parts should go through `DynamicRig` too; one-off moves (doors, food placement) only re-render while they move.

## Ownership boundaries

- The server is authoritative for persistent state, economy, purchases, inventory, plot and building mutations, customer simulation outcomes, and rewards. Client handlers present that state and send requests.
- Shared modules must not depend on client-only or server-only modules. Runtime-specific behavior belongs in `ReplicatedStorage/Handlers` or `ServerScriptService/Handlers`.
- `ReplicatedStorage/Shared/Configs` owns static tuning and registries. Do not duplicate those tables inside handlers. Registry entry types are declared as an authored `Definition` plus the `id` that `Registry.Build` stamps on every entry. A registry's custom methods are typed by an explicit `<Name>Methods` table type, and the registry type is `Registry.Registry<Entry> & <Name>Methods`; annotating `self` with `typeof()` of the built registry is circular and leaves `self` untyped. Instance paths in configs are relative to the package root described under "Authored assets".
- `ReplicatedStorage/Shared/Bus.luau` defines the shared Packet cross-network contracts. The owning server handler validates requests and performs mutations; `Shared/Libs/Signal` supplies in-process events.
- Crystal owns handler startup order through each handler's `dependencies` and `priority`. A handler must declare the handlers it requires instead of reaching into another handler before `Crystal.Run()` finishes.
- Crystal completes all `OnInit` callbacks before running `OnStart` callbacks, with each phase ordered by dependencies and then priority among ready handlers. Startup callbacks are awaited. Dependencies use registered names, including `DataClient` for `DataHandlerClient`; nested support modules do not auto-register.
- `DataHandler` exposes Cloud/Session metatable proxies that track and replicate writes. Mutate through those proxies and use `Shared/DataList` for lists; raw table operations or writes to original tables bypass this contract. Every `Bus.Data.Update` carries the per-player `Revision` declared in its schema (Packet serializes declared keys only); the client ignores an update that is not newer than the last one it applied. `PurchaseHandler` is the sole receipt callback owner and preserves durable deduplication. Gamepasses never reach `ProcessReceipt`: `PurchaseHandler` grants them from the server-side `PromptGamePassPurchaseFinished`, and the server `StoreHandler` appends the pass to `Cloud.Passes` directly because `UserOwnsGamePassAsync` caches its answer per server.
- Coins are whole numbers. The economy was rescaled by 100 (dish prices, tips, upgrade costs, rewards, cash packs, live-event and cat payouts, admin bounds and starting cash), so `EconomyHandler` rounds every credit to a whole coin instead of to cents, and `Economy.XPPerCoin` and `Feedback.Coins.PerCoin` are per coin of the new scale. Saved balances follow through the versioned `Cloud.EconomyVersion` (template value 1). `DataHandler` reads that key from the raw save before `Reconcile` adds it, and `ServerScriptService/EconomyMigration` multiplies `Cloud.Cash` by 100 through the Cloud proxy for a save without it. This runs before a pending progress reset is applied and before `PlayerReady`. The version is written in the same profile save as the balance, so a profile is rescaled exactly once; new profiles start at version 1 with the new-scale starting cash. `Cash` is the only coin-denominated saved value (`Stats.RobuxSpent` counts Robux). Servers still running the old build during a rollout would read migrated balances in the old scale, so a release that ships this should restart all servers.
- Product ids in `Configs/Registries/Products` belong to experience `10590744768` (owned by group `712136202`). Prices and sale state live on the Creator Dashboard only: the client `StoreHandler` reads `PriceInRobux` and `IsForSale` on join and again whenever the Store, Daily or Playtime screen opens (at most once a minute), so a Dashboard change or a failed read corrects itself without rejoining. `PriceInRobux` is the price Roblox charges that player, which can sit below the Dashboard price (a 99-Robux product read 80 for the Studio test account). The Robux plates on the Daily and Playtime screens show the same Marketplace price (or "Off sale") instead of their authored placeholders. Roblox grants a newly created pass to the account that created it. Cash packs are sized against a shift (about 6 000 to 8 000 coins early on): 7 500, 17 500, 50 000, 120 000 and 275 000 coins, intended for 49, 99, 249, 499 and 999 Robux, so coins per Robux rise from 153 to 275 with pack size. Failed/denied calls show an English availability/error message without a delivery claim. `GameInvitePromptClosed` releases busy state for the local player; its recipient list is not used as delivery evidence. UI connections, scopes, press motion, cloned artwork and tasks have explicit cleanup.

## Reward economy and daily playtime

`Configs/Rewards` sizes free rewards against the shift economy. Dish prices and upgrade costs are Lemon Cake's times 100, and with its pacing an early shift (about 4½ minutes with the evening) admits 10–12 guests and earns roughly 2 000–3 500 coins, about 30 000–40 000 an hour; the whole upgrade tree costs 490 650. New profiles (and progress resets) start with 500 coins, Lemon Cake's 5, which is below the first upgrade (Display Counter, 525), so the first purchase comes out of the first shift. Two early prices deviate from Lemon Cake after playtest feedback that levels outran coins: the second table (`cafe_tables`) costs 9 500 instead of 29 050 and grows straight from the Display Counter (Upgrades tree cell `SlotR` instead of `Row4R`), and the second oven costs 5 500 instead of 8 575. `Configs/Progression` uses an XP base of 14 instead of 10, so level 5 takes 155 XP instead of 110 and the whole ladder about 5 500 XP. The 7-day streak (38 500 in total) and the playtime tiers (12 200 a day) each stay around an hour's income and the upgrade tree remains the long goal; the amounts live in `Configs/Rewards`. Promo codes are limited per player by `Rewards.CodeAttempts` (5 failed attempts per 60 seconds; only `unknown_code` and `code_used` count), after which the server refuses with `code_cooldown` until the window ends. The `welcome` code pays 2 500 coins. `CashIcons` thresholds (500/1 000/2 500/6 000) follow the same scale. Cash-pack sizes in `Registries/Products` follow the same shift (see "Ownership boundaries").

Playtime is one track per UTC day (`Playtime.DayLength`, day number = server time divided by it), saved in `Cloud.Playtime { Day, Seconds, Claimed }`. `Session.Playtime.StartedAt` marks the start of the running stretch. The server `RewardHandler.BankPlaytime` rolls a track from an earlier day over (zero seconds, no claims, fresh stretch), then adds the running stretch to `Seconds`, capped at the track's end. It runs every `SaveInterval` (30 seconds) from a process-lifetime loop, before every tier claim, and on leave. `DataHandler:OnLeaving` registers synchronous callbacks that run just before `EndSession`. It is a plain list rather than a `Signal` because the project's Signal is deferred and would run after the session ended. Claims and the Robux skip read the saved track; the skip rolls the track first, so a purchase after midnight pays the new day. The client derives played seconds with the shared `Rewards.GetPlayedSeconds`, treats a stale day as empty, and replaces the authored "Leaving Resets Progress!" footer with "Progress resets daily!" at bind time.

## Limited items

`Configs/Limited` runs limited drops in the style of SuperTag's bundle rotation: one item on sale at a time inside a fixed UTC window (`Drops`, about a month each; never derived from server start), a fixed stock per item shared by every server, each buyer numbered in order. Items bought stay owned for good; when a window ends the next drop goes on sale and everyone can buy again. Between windows the last drop's showcase stays up as ENDED.

Every drop is sold through one repeatable developer product, Registries/Products `limited_slot` (id `3720767346`, `devproduct`, `meta.limited`), so a new drop needs only a `Configs/Limited.Items` entry, a `Drops` row and a Products row of `productType = "limited"` carrying the item's name and bonus. The first drop is the Golden Oven (`golden_oven`, 5 000 copies, 2026-10-21 to 2026-11-21 UTC, row `limited_golden_oven`: `Stat` grant `BurnTimeMult +1`, food burns 30 seconds later). Owning an item adds its row to `Cloud.Passes`, so the bonus is applied by `UpgradeHandler`/`EconomyHandler` like any pass; `StoreHandler.SyncPasses` never removes it.

- **Stock and serials.** The server `LimitedHandler` keeps one DataStore counter per item (store `LimitedStock`; Studio sessions use `LimitedStock_Studio` and topic `LimitedSold_Studio` so tests never touch the live counter or live servers), read on start and every `RefreshSeconds` (60), when it also re-evaluates the drop window. A new drop has its own key, so its stock starts fresh. Granting a copy writes `Cloud.Limited[itemId] = 0` (presence is ownership), then bumps the counter with `UpdateAsync`; the new value is the serial, written over the 0. A failed bump retries `SerialRetries` times and `DataHandler.PlayerReady` numbers any owned copy still at 0. Copies are checked before the prompt but not reserved (SuperTag reserves an order ledger; this game accepts a small oversell window instead): a sale after the last copy is granted anyway (receipts cannot be refused) and logged as oversold. Sales are published on MessagingService with the job id, so other servers raise their count and show the toast; a server ignores its own echo.
- **Buying.** The client `LimitedHandler` adds a Custom-style ProximityPrompt (drawn by `PromptHandler`) to the showcase in the local player's own bakery, enabled while the drop is active, the player does not own the item and copies remain; its action text shows the slot product's live price. Pressing it calls `Bus.Limited.Buy`; the server checks that the item is the active drop, a `BuyCooldown`, ownership, stock and the slot product, records the item in `Cloud.LimitedPending` and prompts the slot. While a prompted item is pending (up to `PendingSeconds`, 30, cleared by the receipt or a dismissed prompt) further requests are refused with `limited_cooldown`, so a second prompt cannot charge for a copy the player is about to own. On the slot receipt (`PurchaseHandler.PurchaseCompleted`) the server grants the pending item, so a receipt arriving after the window rotated still delivers what was bought. A dismissed slot prompt (`PromptProductPurchaseFinished` with `isPurchased` false) clears the pending item. A receipt with nothing pending (a prompt opened outside `Bus.Limited.Buy`) grants only the active drop while copies remain; otherwise it is logged as an error for manual compensation. The server creates `Workspace.LimitedShowcases` in `OnInit`, because the client waits for it before binding showcases. An admin progress reset (`ProgressReset`) keeps `Limited`, `LimitedPending` and `CashBoostSeconds`. A second receipt for an already owned item is logged as an error for manual compensation. `PurchaseHandler` refuses `Bus.Purchase.RequestPurchase` for any `meta.limited` product so the checks cannot be bypassed. Refusals return `UIText` codes `limited_*`.
- **Showcase.** The wall showcase model `GoldenOvenShowcase` lives in `ReplicatedStorage.Assets.Models.Monetization` (inside the `Assets` package, so every place receives it with a package update), at 0.7 scale. The server clones the displayed drop's showcase into `Workspace.LimitedShowcases` once per bakery at `Entrance anchor * Placement`, the kitchen wall beside the ovens, replaces them when the displayed drop changes, streams them atomically, and writes the `Sold`, `Stock`, `EndsAt` and `Active` attributes. The artist's plate shelf at that spot (with its plates and measuring cup) was moved out of all eight bakeries into `ServerStorage.RemovedForGoldenOvenShowcase`; each moved instance carries an `OriginalParent` ObjectValue. The client draws the plaque line once a second (`n LEFT - 12d 4h` counting down to `EndsAt`, `SOLD OUT`, `ENDED`, or `YOU OWN #n` / `YOU OWN IT` from its own profile), turns the rune `SurfaceGui` image and floats the oven for showcases within `AnimateDistance`. The plaque is a larger hanging board added in front of the small one drawn into `GoldTrim` (`PlaqueBoard` gold frame and `PlaqueInset` red fabric, 4.1 by 1.35 studs, its top at the chain ends; the showcase `Placement` is raised to 5 studs so the board hangs above the wainscot ledge), with `PlaqueFace` and its `Label` SurfaceGui resized onto it so the text scales up. The showcase glass is transparent SmoothPlastic because the `Glass` material hides the rune `SurfaceGui` behind it. Its effects are authored ParticleEmitters in the template (`VFX` part: breathing glow and slowly turning rays behind the oven, golden ring pulses, stars from the front; `VFXRim`: sparkles on the arch surface; `Sparkles`: rising sparkles inside), using five Codex-made sprites uploaded as group images (sparkle, glow, ring, rays, star).

## Kitchen and day behavior

- A finished oven or freezer trades places with carried dough it bakes. `Station.Collect` on a Ready or Burnt non-mixing station, while the hand holds dough whose recipe `station` is that kind, replaces the held item with the dish (or Burnt item) in one `InventoryHandler.Exchange` write, sets the station Idle and runs `Station.Load`'s own start (`StartLoaded`: an unfuelled oven goes to Loaded, otherwise Cooking with the door sound), then fires `TutorialEvents.Action(player, "Load", id)` before the dispatcher's `Collect`. It arrives on `Bus.Kitchen.Collect`, so ownership, distance, wall and phase checks are unchanged. The prompt reads Swap. While the hand holds anything else it cannot drop (`CarryPolicy.CanReplace` false), a finished station shows `<label> · Hands full` as a status line instead of a Take the server would refuse. `Exchange` also serves the display shelf (it replaced `ExchangeDish`).
- The mixer stores garden produce the batch cannot use. `Station.Load` with a finite ingredient that the selected recipe does not need or already has enough of, or with no recipe selected, moves it from the hand into the pantry (+1) and succeeds. The prompt reads Store (`<name> to pantry`): with a recipe selected whenever the batch cannot use the item, and with none selected when no mixer dish on today's menu uses it (otherwise the prompt stays Recipes so that dish can be picked). Pantry chips give it back once a recipe needs it; the pantry has no cap. Staples are never stored: an unneeded flour or sugar shows a red `Wrong ingredient`/`Already added` status and its tray offers Put back.
- The mixer prompt offers Recipes only while no recipe is selected. With one selected and the bowl incomplete it shows the status `Needs flour, sugar` (missing ingredients in the card's order), while Add, Store and Mix stay actions. The staple trays (`BuildingViews/Dispenser`) offer Take only while the selected recipe still lacks their staple, and stay silent while the hand holds an ingredient the bowl still lacks; Put back remains for a carried staple the bowl does not need. To change the dish, the floating card's dish name and picture (`MixerBillboardTemplate.Card.FoodName` and `Icon`, bound with `Press` in `MixHandler`) open RecipeToCook.
- A view state with `LineOnly` (together with `Status`) is drawn only as `StationStatusHandler`'s floating line; `InteractHandler` never puts it on the prompt plate, so it cannot take the shared E slot from a neighbouring prop. The mixer's needs and wrong-ingredient lines and every Hands full line use it.
- `RecipePickHandler` closes the RecipeToCook page after Start once the replicated `Cooking.SelectedRecipeId` equals the started dish (within 5 seconds); a refused pick keeps the page open with its failure toast.
- An alert status (a view returning `Alert = true`, currently the oven's "Needs firewood") is drawn by `StationStatusHandler` as a round cream icon holding the carried firewood model (`FoodPreview.ShowItem`) with a red "!" badge, placed in the oven's firebox on the fire part OvenView names `OvenFuel.FirePartPrefix` + building id, 1.5 studs toward the camera and gently pulsing (`StationStatus.AlertIcon`). It stays up beside the oven's own prompt, whose status plate hides alert words: `InteractHandler` copies the flag to the prompt's `StationStatus.AlertAttribute`, which `PromptHandler.StatusLayout` reads.
- An opened bakery stays open until closing time: the entrance prompt (`BuildingViews/Door`) only offers Open Restaurant during Prep and shows the Open sign without an action during the shift, and `BuildingHandler.ToggleDoor` only calls `DayCycleHandler:OpenBakery`. `DayCycleHandler:EndShift` remains for the admin panel's end-shift action.
- The shift follows Lemon Cake's `BP_DailyCycle`: a morning stage (08:00-12:00) and a lunch stage (12:00-16:00), each `DayCycle.StageBaseSeconds + StageSecondsPerLevel × level` (100 + 2.5 × level) seconds, so a shift lasts 3:25 at level 1 and 5:25 at level 25. `DayCycleHandler` fixes the length when the clock starts (opening, or the end of the tutorial's protected service) and stores it as `Session.Day.ShiftSeconds` next to `EndsAt`, so a level-up mid-shift cannot move the clock; the HUD clock and admission read both. Prep stays untimed, unlike the original's timed Start Day stage. `ReportHandler` toasts "Lunch rush!" when the second half begins, like the original's stage notifications.
- After closing time `DayCycleHandler` waits for the guests still inside, like the original: each of them leaves once served or out of patience, so a guest the player is serving is not sent away with the dish on its way. After `DayCycle.ClosingMaxSeconds` (30) only what cannot end by itself is cut off (a protected introduction guest, a body stuck on its way out), and `ClosingHardMaxSeconds` (240) bounds the whole wait; then it enters Summary as an admin early close does.
- `RecipeRequirements.IsObtainable` (station plus every garden/animal ingredient source owned) gates planning: the evening Menu cannot pick such a dish and the server refuses it in `SelectMenu` and `NextDay` (`ingredient_missing`). Opening a day skips the check so an older saved menu cannot lock the bakery; `CustomerHandler` rolls orders only from the orderable part of today's menu. Verified in mock Play: a saved menu with Egg Benedict opened, guests never ordered it, and planning it was refused.
- Today's menu can also change before opening. During Prep, once the introduction is over (`TutorialPolicy.IsActive` false), the bakery header shows the Upgrades and Menu tabs (Report is disabled, Next Day hidden) and `MenuHandler.CanEdit` lets the Menu page edit `Day.Menu` instead of tomorrow's draft. `DayCycleHandler.SelectMenu` applies the same rule: in Prep it validates the picks like the evening planner, writes `Day.Menu` and `Cloud.DayMenu`, and settles idle mixers (`settleMixers`, shared with the start of Prep), so a batch for a dish that left the menu returns to the pantry. During the shift the header returns to the page title and edits are refused (`not_summary_phase`).
- The tutorial bubble keeps `Tutorial.Dialog.HotbarGap` (28) above the hotbar's highest drawn element (slot numbers and item art reach above its frame), not just the frame. The same gap separates it from the side-button column. Above the order row it keeps only `OrderGap` (14), just past its drop shadow, from the cards' drawn labels (their status text sits at the bottom of a taller label box, so the frame's empty top does not count); on phones, where that row sits beside the hotbar, the bubble therefore stays centred and low. Drawn means shown (hidden subtrees are skipped), not fully transparent, and for text, the rendered line. While a page hides the HUD the bubble rests `Tutorial.Dialog.PageMargin` (16) above the screen's bottom edge, over the page's footer rather than the middle of its content, and moves to a bottom corner when that covers less of the page's `MainFrame` (on a wide screen the corner only clips the panel's edge). ## Analytics

`AnalyticsHandler` (server) reports to the Creator Dashboard by observing other handlers' signals; it never gates gameplay, rewards or saves. Studio never sends events: set `Configs/Analytics.PrintInStudio` (off by default) to print each one through the handler's logger instead. Live failures are caught and logged. Event names, funnel steps and day buckets live in `Configs/Analytics` and become dashboard keys, so keep them stable once live.

- **Economy.** `EconomyHandler.AddCash` / `TrySpend` take a `CashReason` (`Gameplay`, `TimedReward`, `IAP`, `Shop`, `Admin`) and an item id, and fire `CashChanged` with the amount that actually moved (pass multipliers included) and the new balance. Sales report the recipe id (through `DayCycleHandler.AddResult`), cat adoptions `CatAdoption`, rewards their track (`Code`, `Daily`, `Playtime`, and `PlaytimeSkip` reported as `IAP` because it is bought with Robux), cash packs the product id and upgrades the upgrade id. `Admin` changes, including `SetAdminCash`, are never reported.
- **Funnels.** `Day` runs once per in-game day: `Prep`, `Opened`, `FirstSale`, `Closed`, `NextDay`; a player who joins mid-day starts at their first step. `Store` runs once per purchase prompt (`PurchaseHandler.PurchasePrompted` then `PurchaseCompleted`), with the product id in the first custom field. `FirstSession` opens a new run when the introduction is completed or skipped (that outcome in the first custom field) and follows the rest of that session: `TutorialDone`, `FirstShiftClosed`, `NextDay`, `SecondShiftOpened`, `SecondShiftClosed`; only the run's next step counts, and the run ends when the player leaves. `Days` has one run per player across sessions (funnel session id = user id): step N (`DayN`) is logged when day N's shift ends, up to `Funnels.Days.MaxDay` (14); players who started before it existed auto-complete earlier days on their first logged one.
- **Onboarding.** The server tutorial `Run` fires `TutorialEvents.Milestone` (name, stage) the first time it marks a milestone while the introduction is active, and for `Completed`/`Skipped`; it marks `Opened` when a shift starts during the introduction. `AnalyticsHandler` logs `Configs/Analytics.Onboarding.Steps` (`Started`, `Mopped`, `PreparedFloor`, `RecipeSelected`, `Mixed`, `CollectedDough`, `FueledOven`, `CollectedDish`, `Opened`, `OrderTaken`, `Served`, `CleanedTable`, `Completed`) to the one-time onboarding funnel. A step is logged only once every earlier step is in the saved `Tutorial.Actions`, so an early action (the door opened before baking, the oven fuelled before mixing) waits and then follows at once instead of auto-completing earlier steps; the Sweep steps count as done past the `Sweep` stage, which old saves and restarted introductions skip.
- **Progression.** `Level` completes the previous level on every level up; `Day` completes the day number when its shift ends.
- **Custom events.** At each shift end, `ShiftCoins`, `ShiftServed` and `ShiftLost` carry the day's totals. Binning burnt food or an unwanted dish logs `DishBurnt` / `DishWasted`. `TutorialSkipped` carries the introduction stage. The first upgrade bought during a `FirstSession` run logs `FirstSessionUpgrade` with the run's current step and the upgrade id. Custom fields only carry low-cardinality values: the coarse day bucket, a product or upgrade id, an introduction stage, a tutorial outcome or a funnel step.
- **Script errors.** `ErrorReportHandler` (server and client) reports each `ScriptContext.Error` as a `ScriptError` custom event, with the realm (`Server` / `Client`) and a script name in its two fields. `Shared/ErrorSource` takes the name from the module at the start of the message, falling back to the blamed script; messages and line numbers are omitted to bound cardinality, and the dashboard's own error report keeps them. The client sends only the name (`Bus.Diagnostics.ClientError`) at most once per script per `Errors.DedupeSeconds`. The server maps names it does not ship to clients to `Other`, deduplicates per player and script, and accepts at most `Errors.ClientPerMinute` reports per player. Server errors deduplicate per script and are attributed to the first player in the server list; they are dropped while the server is empty. Both connections are wrapped in `pcall` so a reporting failure cannot recurse.

## Kitchen ingredient sources

`BuildingHandler/OvenView` closes the authored oven leaves by aligning their local Z width with the line between their fixed hinges. Local X is mesh thickness and is excluded from the angle calculation: the offset between the hinge and bounding-box center previously added about 6.7 degrees of inward rotation to each leaf. Closed leaves now share one plane; their authored open pivots, client tween, cooking-state timing and teardown behavior remain unchanged.

`BuildingHandler/OvenDial` adds a depth-tested SurfaceGui over the inner clock face, behind the authored hand. `OvenView` shows its colored left semicircle only in `Ready` and `Burnt`. Fuel exhaustion and the evening summary cap visual time through `HeatPausedAt` and `PausedAt`. Collection/reset hides the colored scale. The final red mark is rasterized from a polygon following the visible original contour and meets the twelve-o'clock seam; it is not a separate small capsule.

Oven timing follows the installed Lemon Cake build 6596857: all 30 oven recipe bake durations already match `DAT_Recipe.BakeTime` (5–30 seconds); their ready-to-burn interval is 30 seconds, or 60 with `kitchen_burnguard`. The first tutorial bake uses the same 30-second minimum. Fuel remains 90 seconds, or 180 with `kitchen_fuel`, plus a fresh random variation of -10 to +10 seconds. Evidence: `BP_KitchenOven` assigns recipe bake time at bytecode offset 2144, checks the combined bake/burn deadline at 4276, switches to a full burn-time clock revolution and shows `ClockBurn` at 7849, and randomizes fuel at 7097; `WBP_ShopSingle` assigns upgraded burn/fuel durations at 6180/12168. The original `SM_ClockBurn` and `TEX_ClockBurn` supply the left-half layout: gold from 180–270 degrees, orange to approximately 340 degrees, then dark brown with a red burn mark. Roblox uses flat GUI fills and simple marks adapted from those assets; the painted boundary and colors are visual estimates, not recovered gameplay thresholds. Source inspection and geometry checks do not replace an in-game visual test.

`FoodSurfaceView` continuously passes the server-owned ready/burn phase to `FoodModel:SetBurn`, including `HeatPausedAt` and the simulation time used during the day summary. `Shared/FoodBurn` reproduces `BP_Item.MaterialBurn`'s cubic zero-tangent curve: unchanged through 15/30 of the interval, smoothstep to full burn color at 28/30, then hold until the deadline. The upgrade stretches the same curve to 60 seconds. Food retains its texture instead of switching to a flat brown material. `FoodBurnHandler` owns client texture copies for tagged food parts, caches a palette per source color map, processes one image job at a time in roughly 3 ms CPU slices across frames, and restores/destroys materials on removal. PlayerGui viewport food parts also participate in burn rendering and bypass world-camera distance culling. Burnt previews receive an immediate approximate tint while their exact texture copy loads; cleanup restores the original tint. Authored templates outside the local PlayerGui remain untracked. `Configs/FoodTextures` records the color-map URI for each of the 44 recipe/dough meshes, exported from the authored Studio assets; runtime code reads this manifest because both `SurfaceAppearance.ColorMap` and `ColorMapContent` require plugin security. Update the manifest when those authored maps change. Unchanged and fuel-paused fractions do not redraw. The ready-to-burn transition retains the same model/material to avoid flashing a fresh texture. Completed burnt items receive the final fraction as well; existing recipe geometry and inventory identifiers remain unchanged.

Color evidence comes from the actual compiled `MASTER_FoodFade` pixel shader, not the unused `ColorBurn` material-instance overrides: the zlib stream at byte 2778 of its exported `Extras` contains DXBC (offset 92), decoded using Windows `D3DDisassemble`. In linear RGB, each channel uses `overlay(c,k) = c*k` below 0.5, otherwise `1-(1-c)*(2-k)`, with `k=(0.427084,0.176358,0.129414)`. It blends 10% toward the scalar dot product with `(0.141452,0.145833,0.046637)`, then interpolates from the source color by `Fade`. Roblox texture bytes are converted from/to sRGB around this calculation. This is the recovered color operation and timing, not a claim of identical engine rendering: the dynamic color copy is capped at 512 pixels, uses Roblox lighting rather than Unreal's unlit exposure pipeline, and retains the current Roblox food meshes. The original PBR maps stay on the retained authored appearance and are restored on teardown; the dynamic appearance carries the color result only. If editable-image allocation or source access fails, the client logs the reason once per item and uses an explicitly approximate tint fallback. A local Play audit confirmed viewport tracking, immediate tint, fallback completion and cleanup. This Studio experience currently rejects editable-image access until the API is enabled in Experience Settings > Security, so exact texture rendering still requires that setting and a new Play check.

## Sounds

Background music is the client `MusicHandler`: `Configs/Music` lists the soundtrack (`Cake ST1`-`ST3`, uploaded by Increates Cake Game), and the tracks play in order and loop through a `Music` SoundGroup in SoundService. Like Lemon Cake's `BP_Music`, each track fades in over its first `FadeSeconds` (5) and out over its last, so tracks never overlap or cut; a track that has not loaded after `LoadTimeoutSeconds` is skipped for the rest of the session, so a missing or unpermitted asset does not cost a timeout every loop (the playlist stays silent if every track fails). Lemon Cake picks one track per day stage; cake-game has three tracks for its own phases, so it plays them as a playlist. A topbar action (`TopbarHandler:CreateAction`, order 4, labelled "Music: On" / "Music: Off") mutes the music: the client sends `Bus.Player.SetMusicMuted`, the server `SettingsHandler` checks the boolean and saves it as `Cloud.Settings.MusicMuted`, and `MusicHandler` sets the `Music` SoundGroup volume to 0 or 1 and relabels the action from the replicated value. The playlist keeps running while muted, so unmuting resumes mid-track.

`Configs/Sounds` lists the `funset_*` audio assets uploaded by Increates Cake Game, with volume, looping and positional range. The success-feedback sounds (`CashRegister`, `Coin`, `Sparkle`, `LevelUp`, `StationReady`, `OrderUp`, `Purchase`, `Reward`, `Pop`, `StreakMilestone`, `NewRecord`, `FireWhoosh`) are free Creator Store effects, chosen by measuring each candidate in Studio with an `AudioAnalyzer` for an immediate attack (under 0.05 s of leading silence), length and loudness; replace any id freely. `Shared/SoundPlayer` builds configured `Sound` instances: `Create` returns a stopped sound owned by its parent, and `Play` plays a one-shot that destroys itself on `Ended` or after `Sounds.Lifetime`, because servers do not simulate playback; its optional `playbackSpeed` lets repeated feedback climb in pitch. World sounds are created by their server owners under world parts, so they replicate positionally to nearby players:

- `BrushingInteraction` plays `AnimalWash` at the animal; the brushing Janitor stops it on cancellation.
- `CleaningHandler.Clean` plays `Broom` at the character when a sweep is accepted and `BroomSuccess` after the sweep clip's `LockSeconds`; the bakery runtime Janitor cancels a pending chime.
- `CustomerViewHandler.RefreshGuest` plays `WaiterWhistle` at a guest's head when they are ready to order and every `Orders.ReadyWhistleSeconds` (20) until the order is taken, and `OrderUp` when that guest's order is placed (`Choosing` → `Waiting`, by the player or the take-order fallback).

## Success feedback

Every accepted success is presented, never decided, on the client; `Configs/Feedback` owns all of its tuning.

- **Dish sales.** `CustomerHandler.PayForDish` measures what actually reached the wallet (pass multipliers included; nothing once the shift has closed) and fires `CustomerHandler.DishSold` with a grade: table service maps the existing `VFXRules.Reaction` (`Happy` → `Perfect`, `Singing` → `Great`, `Angry` → `Late`; the protected tutorial guest is always `Perfect`), window purchases are `Sold`. The grade is decided before the coins so the service streak can pay: see **Service streak** below. `CustomerViewHandler.Sell` fires the grade's `Configs/VFX` burst at the guest's plate (`FoodSurfaceView` frame; window shoppers burst below the head) for every nearby player, and sends the owner `Bus.Cafe.Sale` (amount, streak tip bonus, grade, streak, new-record flag, guest head, sale position, cash after the credit).
- **The owner's view.** The client `FeedbackHandler` plays the register (pitch rising with the streak; a `Sparkle` flourish for `Perfect`), floats a billboard over the guest (`Popup`: grade caption, the HUD coin with `+N$`, the streak line `xN STREAK +P% TIPS` from two consecutive good sales, and `NEW RECORD!`), and launches 3–12 coins (`CoinFlight`) from the sale's screen point into the HUD coin `Currency.Main.Icon`; off-screen sales launch from the screen edge in their direction. Each landing ticks `Coin` one step higher and punches the icon. `Shared/UI/Stores/Wallet` holds back the part of a sale that the replicated cash already contains but no coin has delivered, and `Components/Hud` shows `cash - Wallet.Hold(cash)`, so the counter climbs as coins land. Each sale records the reported cash, so the counter never dips whichever of the data update and the sale arrives first, and a sale releases itself after `Coins.HoldSeconds`. Sales while a page covers the HUD skip the flight.
- **Service streak.** `Session.Streak` counts consecutive well-timed table sales in the running shift: `Perfect` and `Great` extend it, a `Late` dish or a seated guest leaving unserved ends it (`CustomerHandler.BreakStreak`, which sends `Bus.Cafe.StreakLost` with the lost length), window purchases (`Sold`) leave it alone, and `ClearCustomers` resets it quietly when a shift starts or ends. It is real money: a sale that keeps the streak raises its tip (never the dish price) by `Economy.StreakTipBonusPerStep` (10%) per earlier good sale, up to `StreakTipBonusMax` (+100%), through `Tips.GetSaleValue`'s `streakBonus`. `CustomerHandler.AdvanceStreak` also keeps the day's best in the new `BestStreak` report row (`DayCycleHandler:RecordBest`) and the all-time best in `Cloud.Stats.BestStreak` (added by `Reconcile`; a progress reset clears it); the first sale of a run that beats the record from `Streak.RecordFrom` (3) on is flagged as a new record. On the client, `FeedbackHandler/StreakMeter` draws a flickering flame with `xN` and the next sale's bonus to the right of the HUD coin, following its position (so it leaves with the HUD); it punches and throws embers on every step, burns hotter in three tiers (1, 5, 10), and a lost run of at least `LoseFrom` (2) snuffs into a smoke puff with `STREAK LOST` and the `FireWhoosh` played slowed. Milestones (3, 5, 10, 15, 20, 25, 30, then every 10) play `StreakMilestone` and `FireWhoosh`, show `StreakBanner` (a flame beside bare fire-gradient lettering `HOT STREAK!` / `ON FIRE!` / `BLAZING!` / `UNSTOPPABLE!` / `LEGENDARY!` under a heavy outline, no plate behind it; the run and its tip bonus in white-to-beige so it reads over the warm wood; fire confetti; it waits for a level-up banner that is still up) and fire a `StreakBurst` ring of the oven's flipbook fire at the character's feet. `ReportHandler` adds rows the screen was not drawn with by cloning the authored row named by `Configs/DayReport` `Template`.
- **Level ups.** `Bus.Day.LevelUp` now shows `FeedbackHandler`'s non-interactive banner instead of a status toast: rotating rays (the Store shine `80513051336918`), a generated gold star with the level, a lettered `LEVEL UP!` title (gold gradient under a heavy outline, no plate behind it), the recipes the level unlocks, with `Add it to the menu tonight` for those the player can already make (`Configs/Feedback.LevelUp.Menu*`), screen confetti, the `LevelUp` fanfare and a `LevelUp` burst around the local character. A second level up while the banner is showing restarts it with the new number and no second fanfare.
- **Purchases and claims.** `UpgradeRevealHandler` owns upgrade-purchase sound and world/UI glints from accepted receipts; upgrade data refreshes only repaint/pop the node, so admin grants stay quiet. `FeedbackHandler:Celebrate(gui, sound?)` bursts sparkles and confetti over a visible GUI element. `RewardHandler` celebrates a daily/playtime tile that turns claimed while bound (already-claimed tiles stay quiet on the first refresh). `OrderHandler` punches a card's centre-anchored `Slot` art when its guest's card appears and again when that guest's order is placed (`Configs/Orders.Pop`).
- **Overlay.** `FeedbackHandler` owns one generated `FeedbackOverlay` ScreenGui (`DisplayOrder` 45: above pages and the toast, below tutorial guidance and hints) and a `FeedbackPopups` folder of billboards; pixel sizes scale with the viewport's tighter axis against `ReferenceSize` (1280 by 900, clamped 0.6 to 1.2), so portrait phones follow their width. Level-up, streak and rare-guest banners keep their configured row and size while they fit between the HUD clock (`Time`) and the hotbar less `BannerGap` (`BannerBand` / `PlaceBanner`); otherwise they move down, then shrink. Their fit-to-box text constraints are set in rendered pixels at the banner's scale and floored at `Theme.ScreenScale.MinTextPixels` (10). `Shared/UI/Sparks` (screen confetti and glints) and `Shared/UI/Ease` (timeline curves) are shared helpers. Every coin, piece, popup and banner is destroyed by its owner, and destroying the handler lands the remaining coins so no balance stays held.

## Guest movement

The first admission of each shift is due after `DayCycle.FirstSpawnDelay` (0.5 seconds), prefers a seated guest, and reuses an available unowned pedestrian at the bakery porch without waiting for the street walk or its minimum age. If the friend list is still loading, opening demand allows a generated avatar. The guest then follows the ordinary doorway-to-chair route and finishes choosing in `Orders.FirstGuestChooseSeconds` (one second); the protected tutorial guest then waits for the player's `Take order`. Failed admissions retain opening priority until a body is reserved; tutorial stage gates and table reservations still apply. Later guests retain normal street admission and choosing times. Arrivals follow Lemon Cake's gaps, `DayCycle.GetSpawnInterval(level, progress)`: 15 × (0.95 − 0.01 × level) seconds in the lunch half of the shift and `MorningSpawnMultiplier` (2.5) times that in the morning half (35 and 14 seconds at level 1, 26 and 10.5 at level 25), times the display-flow multiplier; a level-5 shift admits about 12 guests. When lunch begins, the pending arrival is brought forward to `StageFirstSpawnShare` (a fifth) of the lunch gap, as the original restarts its spawn timer. Guests then choose for `Orders.ChooseMinSeconds`–`ChooseMaxSeconds` (4–8 seconds) at the table. Once the introduction no longer gates arrivals, a bakery with no guests at all brings its next arrival forward to `DayCycle.EmptySpawnDelay` (1.5 seconds), so the room never sits empty for a full interval. `CustomerHandler.ReleaseTutorial` also owes `DayCycle.TutorialRushGuests` (1) quick arrival, so the player has work the moment the introduction ends; the slow morning gap then eases a new player in. Rush guests, like the shift's first guest and any guest arriving to an empty bakery, take the porch admission and choose in `Orders.FirstGuestChooseSeconds`. Owned guests walk at `Guests.CafeWalkSpeed` (11 studs per second); the street crowd keeps `WalkSpeed`.

The street crowd is one server-wide set of bodies (`CustomerViewHandler/Street`), capped at `Guests.Street.MaxPopulation` (32); a bakery reserves an existing body it may still visit. `Appearance.Visit` records when each owner last took an identity, and `CanVisit` lets the same face visit that owner again after `Guests.Street.RevisitSeconds` (240), so friend avatars stay one-off visits in the short term. A patrolling body retires at its next circuit node unless a bakery that is admitting guests (`DayCycleHandler:CanAcceptCustomers`, mirrored into the street base's `Admitting` on each `Street.Update`) can still take it. While no bakery is admitting, any registered bakery it can still visit keeps it, so the street stays populated during prep. An idle or AFK bakery therefore never pins the crowd at the cap and starves an active one. Reserved and owned bodies never retire, and a body fading out after a blocked walk is never reserved. Guest rigs use `ModelStreamingMode.Atomic`, like cats, so clients stream each body in whole, accessories and clothing included.

Seated guests no longer order on their own the moment they finish choosing. `GuestState` keeps them in `Choosing` and, once `ChoosingEndsAt` passes, treats them as ready to order: patience starts then (`PatienceEndsAt = ChoosingEndsAt + Patience`, kept when the order is placed), and the player's `Take order` places it. A guest nobody attends orders by themselves after `Orders.TakeOrderFallbackSeconds` (25; 0 restores the old immediate order), so AFK and gamepad players are not stuck; the protected tutorial guest has no fallback. `Shared/GuestOrders` derives readiness, remaining patience, dish names, seat labels (`#N`, `GuestOrders.SeatLabel`), the next need of a guest and per-recipe waiting counts from the replicated record, so cards, bubbles and prompts agree. `CustomerViewHandler.RefreshGuest` whistles when a guest becomes ready and again every `Orders.ReadyWhistleSeconds` until the order is taken (head attribute `OrderCalledAt`).

Every dining place has its own prompt target. `BuildingHandler/View.AttachSeatPrompts` adds an invisible `SeatPrompt<N>` part in front of each chair (`TableMenus.SeatPromptInset`/`Lift`, `SeatPromptDistance` 9 studs), dressed with the table's id and kind plus `SeatPromptAttribute`; the server still validates against the table. `InteractHandler` passes that index as `Context.Seat`, and `GetProp(id, seat?)` returns the table part without a seat and that place's target with one. The `CafeTable` view gives a seat `Take order` (`Guest #N`) or `Serve`; serving is offered with any dish (or unbaked oven dough), labelled `Wants <dish>` and tinted bad when it does not match, so the server's `wrong_dish` / `bake_before_serving` refusals are reachable. The table part keeps `Clean`. Tutorial seat goals keep targeting the table: `Tutorial/Focus` also accepts the active prompt of the goal's seat target. When a seated arrival finds only used places, `CustomerHandler.NoticeDirtyTables` sends `table_dirty` ("Clean the table so guests can sit") at most every `DayCycle.DirtyTableNoticeSeconds` (20).

The guest bubble shows a large `!` in `Orders.Bubble.ReadyMarkColor` with `Take my order!` and pulses while the guest is ready. Order cards also cover eating guests (dimmed, no patience bar) and carry a generated status line over their top (`Orders.CardStatus`): `Choosing`, `Take order!`, the ordered dish, `Serve <dish>` while the player holds it, or `Eating`; below `Bubble.LowPatience` the line turns red and the card art is tinted. The order panel stays hidden without orders. `HydrateHud` keeps it on screen over the pages in `Orders.StaysOverPages` (the recipe pick). `RecipePickHandler` lists dishes guests wait for first and marks them with a generated `N waiting` pill (`Orders.WaitingBadge`).

`StationStatusHandler` (client) floats one outlined line over each own station whose view returns `Status` without an action (`Mixing 5s`, `Baking 12s`, `Needs firewood` in the alert colour when the oven has no firebox for the icon), hidden while that station's own prompt plate is up or a page is open. Labels stay depth-tested so other rooms' walls cover them; because prompt parts can sit inside their model (the oven's lies within its brickwork), each frame lifts the label above the part and pulls it `Forward` studs toward the camera. Studio's MCP screen capture does not draw `AlwaysOnTop` billboards, but does draw these. `Configs/StationStatus` owns its tuning; `InteractHandler.GetParts` supplies the props. Its labels (220 by 34, 24-pixel text) and the firebox icon (72 pixels) are reference pixels scaled by `TextScale.Screen`.

`GuestOrderHandler` floats a speech bubble (`GuestOrderHandler/Bubble`) over each of the local player's seated guests while `Queued`, `Choosing` or `Waiting` (`Orders.Bubble.States`), mirrored from `Session.Customers` and resolved by customer id inside the owner's bakery `Guests` folder; other bakeries' guests get none. The bubble shows the ordered dishes through `FoodPreview` with their names, the seat number badge shared with the order cards (`GuestOrders.SeatLabel`), and the patience left on a clone of the order HUD's bar. Choosing guests show animated dots, ready guests a pulsing `!` with `Take my order!`, queued guests `Need a table!`. New caption words type out letter by letter with the guest's positional `NpcText` blip at the head (`Orders.Bubble.Voice`), BattlesOfEmpires' NPC voice. The bubble pops in, punches when the order is placed, and below `Orders.Bubble.LowPatience` its bar turns red and it wobbles. It lives under `PlayerGui` with the guest's head as `Adornee`, because a `ViewportFrame` inside a `BillboardGui` parented in the Workspace draws nothing, and it uses `Sibling` ZIndex ordering, because the bar's `CanvasGroup` draws nothing under `Global`; and it is not `AlwaysOnTop`, because such billboards draw neither the dish `ViewportFrame` nor the bar's `CanvasGroup`; it has a `MaxDistance`, and it disappears when the guest starts eating, where the dining progress card takes over. It sits `Orders.Bubble.MinHeight` (1.7) studs above the head centre, or `HatMargin` (0.3) above the top of the guest's tallest visible accessory handle (measured when the bubble is created), up to `MaxHeight` (4), so a depth-tested bubble is not hidden inside a tall hat. `Bubble.Layout` draws the `Orders.Bubble` geometry in layout pixels and re-applies it when the dish count changes; `Bubble.SetScale` applies the guest's world scale (`GuestOrderHandler.FitWorld`, every frame) through the bubble's `UIScale`.

The `cafe_window` upgrade grants `WindowSlots` and rebuilds the kitchen window as Lemon Cake's `BP_Counter9` (`IsWindowCounter`): the `Window` building kind is a one-dish `DisplaySlot` dressed onto the authored `Cafe.Upgrades.KitchenWindow` mesh, with its food on the sill (`SurfaceOffset`) and its prompt reachable from the kitchen and the café. It keeps `Session.Window` / `WindowLeftovers`, uses `Bus.Cafe.WindowPlace` / `WindowTake`, and ages overnight like the display. Guests never buy from it. The assistant (`cafe_assistant`) works every job itself, as Lemon Cake's `BP_Assistant` does: every 8 seconds of the shift it takes the first that has work, in order: carrying the window dish to a free display pedestal, serving coffee from the display to a guest waiting for it, clearing a dirty table, moving a finished dish from a station to the display. There is no job to pick and no world character. The upgrade no longer raises `TipMult`, which the original never did.

A seated guest without a free, clean chair does not wait for a table. Following Lemon Cake `BP_Client.FindTable`, the guest becomes a roaming visitor even when no display is bought. `ClientRoam` walks to random points of the shop for 5-15 seconds; `StopRoam` then looks for a cat or a stocked display, and otherwise calls `LeaveShop`. Roaming visitors use the display flow on top of the pedestal browsers (`DisplayCustomers.RoamGuests`). Without a pedestal of their own, they walk between random points of the café runner (`CarpetRoute.RandomPoint`), at least `RoamDoorClearance` from the entrance. The original's random point in the shop's bounding box is adapted here to the runner, the room's authored walkway. A visitor who finds no stock leaves without a patience or streak penalty, as before. The `display_empty` notice (the original's `NoDisplayPastry`) is only sent to bakeries that own pedestals. The table queue now serves only the protected introduction guest: it stands inside, along the wall beside the entrance lane. `SeatQueue` seats queued guests in arrival order, restarts their patience for the walk to the chair, and moves the rest of the line forward through `CustomerHandler.QueueMoved`.

Display slots exist only on bought Display Counter tables (`1ndFloor.Cafe.Upgrades.DisplayCounter.Upgrade1-5`); a dish is never put on the floor. `BaseStats.DisplaySlots` is 0, and the Display kind's `TableUpgrade = "cafe_display"` caps the slot count at that upgrade's level (`BuildingHandler.GetSlotCount`, `DisplayHandler.GetSlotCount`), so tables come only from purchases. Slot N stands on template anchor `display_{N + FoodPresentation.DisplayAnchorOffset}` (anchors 2-6, whose `FoodSurface` attachments sit on the table tops); anchors 1, 7 and 8 lie on the floor by the window and are unused. Every slot is a pedestal guests can buy from (`DisplayHandler` slots 1..capacity). The Bigger Window pass still adds +2 to the `DisplaySlots` stat, but under the cap it adds no slot; its new benefit is an open decision. Verified in mock Studio Play: slots sat on tables 1-2 with food at the table tops, tables 3-5 stayed hidden, and a guest lookup found and took the dish in slot 1.

Every display guest holds its own window pedestal in `DisplaySlot` from spawn until it leaves or goes to adopt a cat; `Spots` routes browsing, roaming, and buying to that pedestal, so window shoppers never stack. A buyer prefers the stocked pedestal it already stands at, skips pedestals other buyers have claimed, and waits while every stocked pedestal is claimed; a browser on the chosen pedestal moves to a free one. Display guests never outnumber pedestals, so a free one always exists.

`CustomerViewHandler` marks eating guests with `Configs/GuestDining` timestamps and a tag using the server-owned `EatEndsAt`. Only explicitly listed handheld recipes receive a held-food attribute; other meals stay on their plate. `BuildingHandler/FoodSurfaceView` replaces the exact guest's held dish with its clean plate, preserving the other seat and dirty-plate lifecycle. `GuestDiningHandler` samples the right arm from the supplied eating animation (`74582433457576`), imported as the authored `ReplicatedStorage.Assets.Animations.EatHand` sequence. Its existing `JointPose` layer preserves seated legs and restores joint transforms before Animator evaluation. Local held food follows that hand; `Clearance` retains the accessory-aware rendered-food correction.

For plated meals, the server mirrors the guest's exact `FoodSurfaceView.Frames[SeatIndex]` position in `EatingPlatePosition`. Private `PlateMotion` clones the authored `ReplicatedStorage.Assets.Models.Cutlery.Fork` and `Knife`: the right hand lifts the fork to the mouth during a 3.2-second cycle, while the left hand cuts near the plate and rests during the bite. Each template has a grip-centered model pivot and a `Tip` attachment; scaling preserves both, and the arm solver derives the reach from the scaled attachment. `PlateArm` computes either R15 shoulder/elbow/wrist pose from the actual joint lengths and applies it through `JointPose`, with bounded reach and a separate outward elbow direction for each side. `Configs/GuestDining.Plate` owns timing, offsets, grip, and scale. Tags support late arrivals; the view retries missing streamed joints or templates and owns all pose, utensil, food, and billboard cleanup. The existing progress card, server meal duration, payments, and guest simulation remain unchanged.

The cutlery was authored in Blender and uploaded through `AssetService:CreateAssetAsync` to the experience's owner, group `712136202`. Fork model `95943767551457` uses mesh `140627453787294`; knife model `78660505687272` uses mesh `105634875740452`. Both use palette image `114369145774713`. The model assets include their grip pivots and tip attachments; load them as `Fork` and `Knife` beneath `Assets.Models.Cutlery` to restore the templates. Published mesh/image IDs are used by ordinary MeshParts; runtime code does not create or upload editable assets. Cutlery templates and imported animation sequences are place-only content and must be saved with the place separately from Script Sync source.

`CustomerViewHandler/Guest` moves every street pedestrian and cafe guest on the shared 10 Hz tick. Humanoid `AutoRotate` stays off: an owned `AlignOrientation` turns the body toward a heading that rotates at most `Configs/Guests.TurnRate` degrees per second, so physics rounds each tick's heading step instead of snapping. The heading aims `LookAhead` studs further along the route and legs hand over at each corner's bisector, so corners become short arcs; `Humanoid:Move` walks along the heading. Pace eases with `Acceleration` and `Deceleration`, drops while the body faces away from its path (turn first, then stride), and on routes with a look-at target slows over the final `SlowdownDistance` studs before the guest stops and turns to face it. That pace is also capped at the speed it can still brake from before the arrival radius (`sqrt(2 * Deceleration * STOP_MARGIN * distance)`, planning with 60% of `Deceleration` to cover the body's lag), so fast walkers such as the workers stop on their spot instead of sliding past it. Routes without a look-at keep their pace, so a route started from the arrival callback continues without a stop. `Street` spaces the crowd through the guest's `SpeedLimit` rather than writing `WalkSpeed`.

Walk playback follows the guest's pace against `Avatar.WalkReferenceSpeed`; 9 studs per second keeps planted feet still on a default R15 rig. Idle, walk, and sit crossfade over `Avatar.AnimationFadeTime`. A seating guest first turns to the chair's facing at the normal turn rate, so the seat tween lowers the body instead of spinning it. The seated state is enabled in the same frame as the explicit sit, so Roblox's touch-to-sit cannot apply its default weld pose first. The facing constraint is disabled while the weld owns the pose; standing up hands orientation back from the body's current facing.

## Reusable hints and tutorial

GUI hints can opt into `IncludeDescendants` for composite artwork. The tutorial clock opts in so its protruding CLOSED sign, ribbon and label share one correctly centered focus rectangle. The tutorial order card opts in too, so the spotlight covers its seat badge and its art while the hover scale grows it past its frame. Invisible/ancestor-clipped descendants are excluded through `HintGeometry.Gui`; the rectangle is recomputed as the HUD scales or animates. The focus hole clips at viewport edges rather than the pointer's padded safe region, which previously cut off the top of this HUD target and made the highlight look vertically displaced.

`Shared/Tutorial/Navigation` redirects an unrelated open page to its close/back button while retaining server-owned tutorial progress. Required recipe pages and the evening Report/Upgrades/Menu flow keep their intended targets. `Shared/Tutorial/UpgradeLesson` adds an optional first-purchase lesson after the first shift: open Upgrades, tap the cheapest unlocked node only when it is not already selected, then press Purchase and see its world reveal. It runs only after the introduction, with an affordable purchase and uncollapsed guidance: first in the first evening, where Nana offers it from the Report before tomorrow's menu (opening the evening Upgrades tab; a player who moves on to the Menu tab has declined it for that evening), and again in a later Prep through the HUD until one is bought. `ShopHandler` supplies client presentation facts for category and the selected purchase level; they never authorize a purchase. `ShopHandler` selects the recommended node when the page opens, so the lesson usually goes straight to `upgrade_buy`. Accepted `BuyUpgrade` actions retire the lesson on the server. Additive `Lessons.UpgradesDue` / `Lessons.Upgrades` flags preserve existing saves, and already upgraded profiles mark the lesson learned at bind time. Close targets resolve the visible, interactable `Exit` or `CloseButton` through `UIHandler`; Inventory, Report, and Upgrades prefer the shared `BakeryMenu` header. Page locks and hidden controls are respected. Closing the page immediately resolves the current gameplay step again.

`Shared/UI/Hint` owns reusable client hints for GUI and world targets. `HintGeometry` handles clipping/projection; `HintSurface` owns a transient, non-interactive overlay; `Configs/Hint` contains visual tuning and the two finger poses. Hints support target resolvers, responsive size, continuous automatic rotation, fixed angles, edge indicators, an authored world arrow beam, stable keys, priorities and optional duration. A single render callback presents the highest eligible priority and releases itself when no owners remain. The finger poses use a manually stepped Ripple tween with quintic easing: rest, press, brief hold, and a slower release. Smooth overlapping opacity avoids the old clamped crossfade, and each hint owns and destroys its motion. Suppressed hints pause their pose phase. The separate text/distance caption below the finger has been removed. `HintRoute` aims world hints at the first doorway when the target is in another room than the player (rooms from `Configs/Hint.Route` floor folders, doorways from the authored `door` models; see [HINTS.md](HINTS.md)). `HintBeam` owns a local clone of `ReplicatedStorage.Assets.VFX.ArrowBeam`, connecting the player to the current 3D target; GUI, hidden and superseded hints disable it. ## Developer panel

The developer panel uses English for labels, confirmations, status, and server responses.

The configured `resetProgress` action has one button in a fixed red **Danger zone**, above the ordinary scrollable actions. Short viewports reduce the action-list height before scaling the panel. Confirmation replaces both areas and shows the server's selected-player identity, irreversible deletion/disconnection warning, and paid-ownership preservation. Request controls disable while waiting; cancelling, closing, changing target, target departure, access removal, and local expiry discard the pending confirmation. Closing while a request is queued prevents that request from being sent; an already submitted mutation remains server-owned. Confirmation timers and request tasks belong to the panel's Janitor. The existing server confirmation and reset owners remain unchanged.

`AdminPanelHandler` creates an owned developer overlay, opened with **F4**, **/admin**, or its **ADMIN** button. The button has its own `AdminToggle` ScreenGui at the right end of Roblox's topbar row (`TopbarSafeInsets`, `Configs/Admin.Toggle.RightClearance` clear of the tutorial's help button), so it never covers a HUD group; touch screens show `ADMIN` without the F4 hint at a 44-pixel height. It does not replace authored `MainGui` screens. Player selection is limited to the current server; the panel supports status inspection, exact coin grants/balance replacement (without paid multipliers), XP, pantry stock, upgrade grants/budget, tutorial restart/skip, day transitions, hand cleanup, respawn, and full client data resynchronization. Actions call the existing owning handlers, preserving their signals, caches, state machines, and proxy writes.

Tutorial actions report a refusal while `Configs/Tutorial.Enabled` is false; the panel does not override the game's global tutorial switch. Day actions retain the existing phase/menu requirements and report refusals instead of forcing invalid state transitions.

`AdminHandler` authorizes every `Bus.Admin.Request` on the server. Published servers use the existing UserId allowlist in `ServerScriptService/Cmdr/Admin.luau` (currently `codebykoi` and `funseti`); add another developer's numeric UserId there and deploy the source change. Studio permits local test players. Roblox edit/collaboration permissions are not automatically treated as runtime admin access. The replicated `AdminPanelAccess` attribute controls presentation only and never authorizes a mutation.

Every panel mutation requires an expiring, one-use server confirmation bound to its executor, target Player instance, action, and amount. Requests validate finite integer quantities, action-specific limits, profile readiness, and pending resets; executor throttles and target locks prevent overlapping panel operations. Unknown actions and arbitrary data paths are rejected. The server Output records attempts/results with executor and target IDs; the panel exposes the last 30 results from this server's memory, not a durable cross-server audit service. Offline edits, bans, receipt grants, and arbitrary code execution are not exposed.

Progress reset uses `DataHandler:RequestProgressReset`: save the pending marker, end the session, and apply new-player defaults before `PlayerReady` on rejoin. It now starts with normal starter cash rather than an upgrade budget. Paid passes, skins, receipt deduplication, and `Stats.RobuxSpent` survive. The separate upgrade-budget action remains available. `DataHandler:ResendSnapshot` flushes preceding deltas and resends both stores using the existing snapshot/revision channel.

For isolated Studio QA, set the attribute `AdminTestMockData = true` on **ServerScriptService.Handlers.DataHandler** in Edit mode before starting Play, then remove it after stopping. `DataHandler` honors it only in Studio and uses ProfileStore.Mock; the configured live store and saving policy remain unchanged. The panel shows `STUDIO MOCK` when this mode is active. Ordinary Studio Play still saves real data when `StudioSavingEnabled` is true. Reset/rejoin persistence must be checked separately: a fresh Play session does not retain the in-memory mock store.

## Admin abuse live event

An imitation developer "admin abuse": giant avatars of studio members stand past the south end of the street and talk in scripted dialogues, golden guests pay five times more, and cupcakes fall around every player. The researched engine limits behind it are in [mem/admin-abuse.md](mem/admin-abuse.md).

Every tunable lives in `Shared/Configs/AdminAbuse`: the cast (UserId and role per id), dialogue scripts as `{ Speaker, Text, At }` lines with a per-script `Duration`, the stage (origin, look-at point, spacing, `Model:ScaleTo` factor; bubble size follows the scale), speech and HUD presentation, golden guest rate and cap, cupcake rain numbers (coins, per-player cap, active cap, interval, radii, fall and life time), the relay topic and lead time, and the UTC schedule. Avatars and display names are read at runtime, so dialogue text never names a cast member. Adding a script adds an admin panel start button automatically.

A running event is only `{ Id, ScriptId, StartsAt }`, where `StartsAt` is an absolute `workspace:GetServerTimeNow()`. `Shared/LiveEventTimeline` derives the cast on stage (speakers in order of their first line), the end time and the line on screen from that state and the config; server and clients share it, so no dialogue text crosses the network and late joiners land on the current line.

Server `LiveEventHandler` owns the event on its server:

- `Start(scriptId)` / `Stop()` apply the change locally and publish it on one MessagingService topic (`Relay`). Payloads are compact (`k`, `i`, `s`, `t`) and validated on receipt, including a start time within `[now - Duration, now + LeadSeconds + StartSlackSeconds]`; a failed subscription retries every `Relay.SubscribeRetrySeconds`; the starting server re-broadcasts the state every `Relay.RebroadcastSeconds` because delivery is best effort. Ids that ended or were stopped are remembered, so late copies never restart them.
- `Schedule` computes UTC slots identically on every server and derives the event id from the slot, so scheduled events need no messaging. It is off unless `Schedule.Enabled` is set.
- Each event gets a Janitor scope holding the giants (`CastRig`) and the rain (`CupcakeRain`), destroyed on end or stop. `CastRig` reuses the guests' avatar cache in `CustomerViewHandler/Appearance` (pcall, per-server cache, retry cooldown), scales with `ScaleTo`, stands each giant on the ground found by a ray under its slot, anchors every part in the rest pose, disables collision/touch/query, marks the model `Persistent` for streaming and stores `CastId`/`DisplayName` attributes. Anchoring only the root does not work: avatar rigs use physical `AnimationConstraint` joints that the Humanoid drives as a ragdoll, and a giant's body sags hundreds of studs away from its pinned root, even with kinematic joints. Runtime instances live under `Workspace.LiveEvent`.
- `CupcakeRain` drops a cupcake from `Assets.Models.Cake.CarrotCupcake` on a raycast floor point in a ring around each player, reachable in a straight line from them. The model is placed at its landing spot with a `LandsAt` attribute; the server collects it when the owner's root part is within `PickupRadius` after landing and the owner's profile is loaded (otherwise the drop stays until it expires). Each rain step runs isolated, so an error is logged once and the rain continues. The private `Physics` module makes the cast and the drops inert and builds their raycast filters. There is no client request to trust: reward, per-event cap (per UserId, so rejoining does not reset it) and active cap are server decisions. Income is `EconomyHandler:AddCash(..., "Gameplay", "LiveEventCupcake")`.
- `PickGuestType` lets `CustomerHandler.SpawnCustomer` replace a seated arrival with the `event_guest` customer type at `Guests.Chance`, up to `Guests.MaxActive` per bakery, never during the tutorial. `PayForDish` multiplies a dish payout by the type's `coinMultiplier` (5). The existing rare guest banner announces it with an `x5 COINS` chip.

Access goes through the existing admin paths only: `/liveevent start [script]` / `/liveevent stop` (Cmdr `Admin` group) and the **Live event** section of the developer panel, whose actions are marked `global` in `Configs/Admin` and skip the selected player's profile. Both reach `LiveEventHandler:Start` / `Stop`.

`Bus.LiveEvent` carries `State` (push on change), `Get` (state for a client that just started listening) and `CupcakeCollected` (position, credited coins, balance for the HUD coin flight). Client `LiveEventHandler` updates on Heartbeat: a generated `LiveEventBanner` overlay shows the countdown, time left and the speaker's headshot (`rbxthumb` AvatarHeadShot), display name, role and line, centred just below the HUD clock (`FeedbackHandler:BannerBand`) at `TextScale.Screen` density, no wider than the screen less `Hud.SideMargin`, text floored at `Theme.ScreenScale.MinTextPixels` (10); `Speech` puts a stud-sized BillboardGui bubble over the giant's head (not `TextChatService:DisplayBubble`, whose bubbles fade beyond `BubbleChatConfiguration.MaxDistance`); each line is mirrored to the `RBXSystem` chat channel. `Rain` animates the fall locally and hides other players' cupcakes, which this player cannot collect.

Studio verifies the single-server path. The cross-server relay can only be verified in the published game with two or more servers.

## Validation workflow

- `rokit.toml` pins Selene, StyLua, luau-lsp, Wally, and wally-package-types. Run tools through Rokit from the repository root.
- `scripts/check.ps1` is the verification gate: it regenerates the sourcemap, runs `selene .`, fails if any first-party `.lua`/`.luau` file does not start with `--!strict` (files matching `luau-lsp.ignoreGlobs`, the Wally packages and vendored libraries, are exempt), then runs the pinned analyzer over every source root: `luau-lsp analyze --platform roblox --definitions <globalTypes.PluginSecurity.d.luau> --sourcemap sourcemap.json --settings .vscode/settings.json ReplicatedFirst ReplicatedStorage ServerScriptService ServerStorage StarterCharacterScripts StarterPlayerScripts`. Definitions are resolved from `.zed/.cache` first, then the luau-lsp extension's Cursor/VS Code global storage; pass `-Definitions` to use another copy.
- Analysis uses luau-lsp's default type solver, matching the editor. Two shared shims exist because of it: `BaseStats.StatKey` is an explicit key union (no `keyof`), and `Shared/UI/Scope.luau` wraps `Flux.scope` for callbacks that return nothing. Flux selectors (`Find.Path`, `Find.Child`) are given plain signatures where they are used.
- Every first-party module is `--!strict`, so Studio's Script Analysis checks it strictly too. Three solver limits shape strict code here: a runtime-resolved `require` (Crystal's handler discovery, Cmdr's generated `CmdrClient`) is written `(require :: any)(module)` because strict mode rejects paths it cannot resolve; an instance built with `setmetatable` is only assignable to its own class type, so a field holding one uses that type (`Building.FoodVisual: FoodSurfaceView.FoodSurfaceView?`) instead of a structural interface; and reassigning a `T?` local inside `if not x then` does not narrow it afterwards, so use `existing or create()` or an early return.
- The editor runs Roblox's live FFlags while the CLI enables all stable flags, so the editor can be stricter about missing optional table fields. Config-style inputs therefore get their own input type (for example `StateMachine.StateDefinition`, the registry `Definition` types) rather than reusing the fully-populated runtime type.
- `.vscode/settings.json` and `selene.toml` exclude the Wally directories and the vendored libraries from diagnostics and lint. DataModel diagnostics use luau-lsp's default `strictDatamodelTypes = false`; the filesystem sourcemap cannot describe place-only assets such as `ReplicatedStorage.Assets`. Zed explicitly uses the same setting. This does not disable `--!strict` Luau checking; authored instances can be declared as an `AuthoredScreen`-style intersection type at the point of use.
- Formatting follows StyLua defaults; `.styluaignore` mirrors the lint exclusions. The `--[[ Section ]]--` header comments are rewritten by StyLua, so a repo-wide `stylua --check` is not part of the gate.
- The luau-lsp Studio companion plugin talks to the editor on port `3668` (`luau-lsp.studioPlugin.port`), shared with the other projects the Studio plugin is configured for, with `maximumRequestBodySize` raised to `50mb` because this place's DataModel dump exceeds the 3 MB default. Only one workspace can own the port at a time.

## Zed on Windows

Install Zed's `Luau` extension (`4teapo/zed-luau`), run `rokit install`, then `scripts/setup-zed.ps1`. The setup script caches Roblox PluginSecurity definitions and API docs in the ignored `.zed/.cache` directory and installs `4teapo/luau-lsp-proxy` v0.1.0 into the Luau extension's work directory. Use `-Refresh` to refresh these downloads. `scripts/check.ps1` can then run without VS Code or Cursor installed.

`.zed/settings.json` uses the Rokit `luau-lsp` and `stylua` commands from PATH, enables workspace diagnostics, and mirrors the project's vendor exclusions. DataModel diagnostics match VS Code and the CLI; enabling `strictDatamodelTypes` without a complete Studio tree reports missing place-only children. Zed uses stable CLI flags without live Roblox flag downloads or the experimental solver. StyLua runs on an explicit format command and respects `.styluaignore`; saving alone does not reformat existing section comments.

The Studio companion connects through the proxy on port `3668`. The proxy accepts compressed DataModel updates; the VS Code `maximumRequestBodySize` setting does not apply to it. Close the other editor's Luau workspace before using this port in Zed.

Use `task: spawn` for the project tasks in `.zed/tasks.json`: tool/package installation, Zed setup, the full check gate, and sourcemap generation. Zed's Luau extension does not run the VS Code sourcemap generator. After adding, removing, moving, or renaming scripts with Studio's Script Sync inactive, run `Regenerate sourcemap` (the check and package tasks also regenerate it). Source-content edits do not require regeneration. The generator and Selene exclude Zed's generated definitions from game source.
