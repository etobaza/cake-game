# Architecture

## Repository guidance

Repository content is English-only: documentation, memory notes, source comments, user-facing strings, tooling, and generated reports follow the mandatory [repository language rule](AGENTS.md#repository-language-mandatory). Generators must preserve this rule when rebuilding their output.

`AGENTS.md` is the shared session/startup and verification contract. `CODE_STYLE.md` defines Luau conventions for new and touched code; `PACKAGES.md` maps the actual dependencies and call-site boundaries. `CLAUDE.md` and `GEMINI.md` import the shared rules, while `.github/copilot-instructions.md` directs Copilot to them and includes the core verification requirements. Cursor uses root `AGENTS.md` directly. Zed's filename precedence selects the Copilot entry here, which directs it to the shared rules. `AI_INSTRUCTIONS.md` records discovery behavior, limitations, and new-session checks. Keep these entry files thin instead of maintaining independent architecture copies.

Generated sourcemaps, installed Wally packages, logs, temporary files, editor backups, and operating-system metadata are excluded through `.gitignore`. Keep dependency manifests and lock files under version control.

Reference research lives in [Exeperience/LemonCake](Exeperience/LemonCake/README.md), with a short retrieval guide in [mem/lemon-cake.md](mem/lemon-cake.md). The Lemon Cake snapshot records Steam build identity, extracted data, Blueprint indexes, reproduction tools, and verification limits. Original extracted assets and full dumps stay in its ignored `.local` cache. These folders are documentation/research tooling, not Roblox runtime source roots; the reference does not override this project's architecture or adapted balance.

## Runtime layout

The repository mirrors Roblox DataModel services on disk. Studio's Script Sync keeps the place and this folder in step (scripts only; it maps directories literally, so a directory holding `init.luau` is that script with its siblings as children, and `.client` / `.server` / `.legacy` suffixes pick the script class). `.vscode/generate-sourcemap.ps1` applies the same rules to produce `sourcemap.json` for the Luau Language Server, so the gate works with Studio closed. Script Sync also writes its own `sourcemap.json` (absolute paths) whenever it syncs; the two are interchangeable for luau-lsp, and neither is edited by hand or committed.

`StarterCharacterScripts` and `StarterPlayerScripts` live at the repository root and are mapped under `StarterPlayer`.

- `ReplicatedStorage/Client.client.luau` is the client bootstrap. It loads `CmdrClient` when present, registers every direct child module of `ReplicatedStorage/Handlers` with Crystal, then calls `Crystal.Run()`.
- `ServerScriptService/Server.legacy.luau` is the server bootstrap. It registers Cmdr hooks, types, and commands from `ServerScriptService/Cmdr`, registers every direct child module of `ServerScriptService/Handlers` with Crystal, then calls `Crystal.Run()`.
- `ReplicatedStorage/Handlers` contains client handlers. `ServerScriptService/Handlers` contains server handlers. Crystal loads a handler only when it is a direct `ModuleScript` child of those folders; nested modules are required by their handler.
- `AmbientMotionHandler` loads shared clips from `ReplicatedStorage.Assets.Animations.Ambient`, skipping non-`KeyframeSequence` children and unreadable clips with loop guards. Missing clips do not prevent visual setup; a missing folder prints a diagnostic message.
- `ReplicatedStorage/Shared` contains code and data safe to require from either runtime: Crystal, the bus, configs, UI, shared gameplay views, and utility libraries.
- `ReplicatedStorage/Shared/Libs` holds `Logger` and `StateMachine` (project code) next to vendored third-party libraries: `Packet`, `PartCache`, `Ripple`, and `Signal`. The vendored ones are committed as-is and excluded from lint and type analysis.
- `ServerScriptService/Cmdr` contains Studio/admin command definitions. The client command surface is `ReplicatedStorage/CmdrClient`, created by Cmdr at runtime.

## Authored assets

Authored content ships as Roblox Packages (`PackageLink`) and lives in the place: `Workspace.World` (bakeries, environment, roofs, and spawn), `ReplicatedStorage.Assets` (prompt billboard, animations, model templates, source art, and VFX), and `StarterGui.MainGui` (every ScreenGui). These package roots add a wrapping folder, and code addresses the contents relative to it:

- `ReplicatedStorage/Shared/World.luau` is the only place that knows the world package's location. `World.Root` / `WaitForRoot` find `Workspace.World`; `World.Bakeries` and `World.Find(path)` resolve below it. Configs that name world content (`Base.BakeriesFolderName`, `Traffic.RoadPath`, `Traffic.Signals.Path`, `Guests.Street.SidewalkPath`) are child-name paths relative to that root, never to `Workspace`. Templates that are cloned rather than placed (building models, food, tools, traffic vehicles, and cats) live under `ReplicatedStorage.Assets.Models`. Anything else the game needs from the world must go through this module rather than `workspace:FindFirstChild`.
- `ReplicatedStorage.Assets.Models.Cats` contains the four original `cat` rigs. `CatHandler` reads the folder named by `Cats.TemplatesFolder` and keeps its existing MeshId sort, preserving saved variant indices. Its prepared runtime copies remain in `ServerStorage.CafeCatTemplates`; spawned cats belong to their bakery.
- `ReplicatedStorage.Assets.SourceModels` preserves the remaining 105 artist originals formerly staged in `Workspace.World.Assets`, including duplicate names and the original cake folder. This reference-art collection is outside `Models` so `Buildings.FindAsset` cannot accidentally select an unprepared duplicate. Names, pivots, meshes, and existing prepared model paths are preserved. The embedded plant animation script is disabled in this collection (`SourceTemplateWasEnabled` records its previous state), so stored source art does not animate. Promote usable templates into the appropriate `Models` category deliberately. Asset reparenting and script enabled state are place changes; Script Sync does not serialize them, so save the edited place separately from the source commit.
- `UIHandler` waits for `PlayerGui.MainGui` (`SCREENS_FOLDER`) and hands that folder to `Shared/UI/App` as the root that all screens are looked up under. Nothing else looks up an authored screen by name in `PlayerGui`; drivers go through `UIHandler:GetPanel` / `GetHud`.
- `MenuHandler` preserves the authored empty selected-recipe plate's darker background, border, geometry, font, and text color. Its caption reads `Empty`, with both text layers horizontally centered inside the centered status container. Empty plates remain passive placeholders without a food viewport and continue toggling with the existing filled plates as recipes are selected.
- `RecipePickHandler` fits the recipe list to its authored container and centers the existing rows with a permanent scrollbar inset. Eight logical pixels above and below the list protect selection outlines from clipping. Its canvas follows the list layout's visible content height, converted out of `UIScale`, plus both edge insets so the last row remains reachable after menu or viewport changes.
- `MenuHandler` gives both dietary bonus states matching 24-pixel logical rows with a 4-pixel gap and a shared left edge. The footer reserves additional space in wide, compact, and short layouts by moving or shortening the selected-recipe strip and reducing the recipe grid where needed; earned/unearned visibility and bonus values remain unchanged. Local preparation helpers own status text, bonus row styling, and responsive footer geometry; `CollectBonuses` identifies and stores the earned/unearned pairs.
- `ReportHandler` sizes the authored daily report rows to share the full content height with 8-pixel logical gaps on both wide and compact canvases. Captions and numbers have matching 20-pixel logical side insets and a reserved gap between their columns. Row text uses a 32-pixel logical maximum, headings and profit text use 34, and paired labels are vertically centered and shrink to fit their available width. It hides the old `Middle.Lines` dashed inset, which would otherwise draw over the first and last rows. It updates the existing responsive size attributes and text baselines so viewport changes preserve the larger layout; the fixed report canvas does not grow with its scaled rows.
- `Shared/UI/BakeryMenu` owns the shared header for Report, Menu, and Upgrades. During `Summary`, the header shows only Report, Menu, and Next Day in three equal-width slots, vertically centered with 8-pixel logical gaps. The outer tab edges align with the page background's 6-pixel logical side insets. The existing ribbon artwork extends 64 logical pixels to the left so its triangular tail sits outside the page; the header moves up 22 logical pixels, leaving an 8-pixel gap above the page background. An explicit right anchor and matching wide/compact row sizes and header positions preserve alignment after resizing; each tab's dashed inset is centered as well. The row reclaims the hidden close button's space; `ReportHandler` permits only Report and Menu in the evening modal, so Upgrades cannot open through the HUD either. Outside that phase, HUD-opened pages bind the authored full-size `Header.Title` from StarterGui, with the existing close control. Upgrades remains available through the HUD outside the evening modal.
- `StarterGui.Mikey` supplies the authored visual reference for `StarterGui.MainGui`. Matching controls use its colors, fonts, backgrounds, corners, strokes (including stroke sizing mode), and gradients directly in the place. Report and the shared bakery header reuse that palette and decoration. The appearance pass preserves outer panel dimensions and gameplay layouts. Internal Funds, reward-card, recipe-card, and ribbon proportions follow the reference within those dimensions. Semantic icons use `ScaleType.Fit`; tiny rotations are removed from scrolling content to preserve clipping. Selection outlines respect authored scaled stroke thickness. Reference ScreenGuis under `Mikey` stay disabled so their sample HUD does not overlap the live HUD. Place asset changes must be saved with the place separately from Script Sync source.
- `ReplicatedStorage.Assets.VFX` holds one flat `BasePart` per effect named in `Configs/VFX.Effects` (plus `OvenFire`), carrying the emitters and the placement attributes `VFXHandler` reads (`SourceOffset`, `SourceFoodSize`, `SourceToolSize`, `BodyOffset`). These parts were extracted from the artists' staging rigs (the `SourcePath` attribute records where); the rigs themselves are not part of the place. Author a new effect by adding a part here and a row in `VFX.Effects`, never by shipping a rig.
- `StarterGui.ResetPlayerGuiOnSpawn` is `false` in the place. Every screen was already `ResetOnSpawn = false` and is bound once by the client, but a Folder in `StarterGui` has no such property: with the default setting Roblox destroys and re-copies the whole `MainGui` folder on respawn, which leaves the client holding dead screens. The place-level setting keeps `PlayerGui` intact across respawns. Do not turn it back on.

`ShopHandler` preserves the authored upgrade-node stroke thickness during selection. Availability still determines node colors, while selection updates the footer and plays the existing press animation; selection does not replace the cream fill with white or thicken the border. All three category tabs use the Store/Kitchen background image so Greenhouse has the same thin border.

The place-authored category connector frames use two-pixel strokes with integer-aligned, overlapping endpoints to avoid gaps at right-angle joints. Kitchen's unused final-slot connector is hidden. The crowded Store branch enters Display Counter 3 from the side rather than sharing two nearly adjacent horizontal routes. Collinear overlapping segments are merged. Connector repairs preserve node sizes, positions, and upgrade requirements.

The authored `StarterGui.MainGui.BakeryMenu.MainFrame.Header.Buttons.NextDay` uses the same idle background and white caption styling as Menu. Its background has no `UIStroke` or `UICorner`; the shared red ribbon supplies the outer frame. Text outlines and the dashed inset remain. This appearance is a place-only edit and must be saved with the place separately from source changes.

`Shared/UI/OrderLayout` sizes the authored order HUD from its active card count, capped at four visible cards with horizontal scrolling for additional orders. Short portrait screens show fewer slots to keep cards clear of the side buttons and currency. `Configs/Orders.Layout` owns card dimensions, spacing, and a maximum scale of 1.25. `HudLayout` reapplies the layout when the viewport or `OrderCount` changes; rows that cannot fit to the right of the hotbar move above it. The ribbon and caption stay inside the computed rectangle, and `OrderHandler` sizes cards using the visible slot count instead of reserving four slots for a single guest.

`RunHandler` binds the existing authored `Controls.Run` through `Shared/UI/RunControl`. The button uses a translucent dark circle, light ring and caption, with a light active state. `Configs/TouchControls` owns its visual ratios and spacing. Its size and position follow the actual Roblox `TouchGui.TouchControlFrame.JumpButton` bounds across viewport changes and control recreation: above the small phone control, left of the larger tablet control. Coordinates are converted into the HUD container's space so GUI insets do not shift the pair. Run stays hidden until a visible jump control is available; keyboard and gamepad sprint bindings remain independent.

`Shared/UI/Format.Number` rounds displayed amounts to the nearest whole number and groups thousands with spaces. The HUD balance, upgrade funds and prices, recipe prices, reward cards, and daily profit use this shared formatting. HUD and upgrade-fund animations also step through whole numbers. `Shared/UI/ButtonRow` gives the shared bakery header, recipe filters, and upgrade categories coordinated hover and selection feedback. Each row owns its wrappers, motions, and input connections; hidden or disabled controls and focus loss clear feedback, and cleanup restores the authored children. No place-only edits are required.

## Dependencies

Wally owns every registry package. `ReplicatedStorage/wally.toml` lists the shared-realm packages (`cmdr`, `flux`, `janitor`, `topbar-plus`, `typed-promise`) and installs into `ReplicatedStorage/Packages`; `ServerStorage/wally.toml` lists the server-realm packages (`profilestore`) and installs into `ServerStorage/ServerPackages`. Both install directories are gitignored; the manifests and lock files are committed.

Run `scripts/install-packages.ps1` after cloning or changing a manifest. It installs both manifests into a unique temporary directory outside the synced project, then flattens each package into the layout Script Sync understands: Wally emits Rojo projects (`_Index/<package>/<name>/default.project.json` pointing at `src/`, `lib/`, or one file), which Script Sync would mirror as a Folder and break every link `require`. Flattening keeps the mapped runtime root, discards the surrounding development/test tree, moves that root up so `<name>/init.luau` is the package, drops non-script files, and renames `.lua` to `.luau`. The installer verifies every package root, generates a temporary sourcemap, and runs `wally-package-types` before replacing the watched package directories with the complete trees. It then copies back the lock files and regenerates the project sourcemap. Failed installation restores the previous package directories. Never install or flatten raw Wally output inside the watched directories: Script Sync can import intermediate folders and test runners, then write that stale hierarchy back to disk. Never run `wally install` on its own.

After installation with Studio open, verify all seven `_Index/<package>/<name>` roots are `ModuleScript` instances and `ServerStorage.ServerPackages` exists before starting Play. The bundled Promise development runners (`runTests` and `modules.testez.test.runner`) must not exist in the installed runtime. Restart Play after synchronization and check both client and server startup; a passing disk analysis does not establish that Studio imported the same hierarchy.

## Ownership boundaries

- The server is authoritative for persistent state, economy, purchases, inventory, plot and building mutations, customer simulation outcomes, and rewards. Client handlers present that state and send requests.
- Shared modules must not depend on client-only or server-only modules. Runtime-specific behavior belongs in `ReplicatedStorage/Handlers` or `ServerScriptService/Handlers`.
- `ReplicatedStorage/Shared/Configs` owns static tuning and registries. Do not duplicate those tables inside handlers. Registry entry types are declared as an authored `Definition` plus the `id` that `Registry.Build` stamps on every entry. A registry's custom methods are typed by an explicit `<Name>Methods` table type, and the registry type is `Registry.Registry<Entry> & <Name>Methods`; annotating `self` with `typeof()` of the built registry is circular and leaves `self` untyped. Instance paths in configs are relative to the package root described under "Authored assets".
- `ReplicatedStorage/Shared/Bus.luau` defines the shared Packet cross-network contracts. The owning server handler validates requests and performs mutations; `Shared/Libs/Signal` supplies in-process events.
- Crystal owns handler startup order through each handler's `dependencies` and `priority`. A handler must declare the handlers it requires instead of reaching into another handler before `Crystal.Run()` finishes.
- Crystal completes all `OnInit` callbacks before running `OnStart` callbacks, with each phase ordered by dependencies and then priority among ready handlers. Startup callbacks are awaited. Dependencies use registered names, including `DataClient` for `DataHandlerClient`; nested support modules do not auto-register.
- `DataHandler` exposes Cloud/Session metatable proxies that track and replicate writes. Mutate through those proxies and use `Shared/DataList` for lists; raw table operations or writes to original tables bypass this contract. Every `Bus.Data.Update` carries the per-player `Revision` declared in its schema (Packet serializes declared keys only); the client ignores an update that is not newer than the last one it applied. `PurchaseHandler` is the sole receipt callback owner and preserves durable deduplication.
- Third-party code under `ReplicatedStorage/Packages`, `ServerStorage/ServerPackages`, and the vendored `Shared/Libs` entries above is not application code: fix call sites, not the libraries.
- First-party direct diagnostics use ordinary `print` instead of `warn`, preserving message content and control flow. Existing Logger levels remain available; its warning-level console output already uses `print`. Generated and vendored diagnostics are unchanged.

## Kitchen ingredient sources

The garden sink and watering can are starter fixtures. `PlotHandler` prepares the existing `Garden.Upgrades.CrystalWater.Upgrade.Part` through its private `BuildingHandler/SinkWater` helper, giving it a translucent water surface and owned ambient droplets. `Configs/Garden.SinkWater` contains the authored path and presentation tuning. Both occupied and vacant bakeries retain this water; `UpgradeViewHandler` does not gate it on `garden_water`, and `VacantView` excludes it from upgrade hiding. The existing Crystal Water stat still doubles plant moisture duration. This follows installed Lemon Cake build 6596857: `LVL_Game.BP_Counter_6` starts with `WateringCan`, the independent `PS_WaterTricle_2` emitter runs at two droplets per second with a 0.75-second lifetime, and `WBP_ShopSingle.UnlockCrystalWater` sets plant dry rate to 0.5. The translucent Roblox basin surface, texture and dimensions are an adaptation, not recovered original rendering. These presentation changes are prepared from disk-backed source at startup and need no place-only asset edits.

Garden harvest prompts show the ingredient name without a stock/capacity counter. Availability still follows the server-owned stock.

Animal brushing chooses the nearest authored cow/chicken body in the source's care variant, rather than the first mesh in a flock. Begin and continuation use the same horizontal reach, so the height of a chicken cannot immediately cancel an accepted action. Clean and dirty animal meshes are mutually exclusive at the configured cleanliness threshold; these are complete opaque skins, so rendering both as a dirt fade produced duplicate silhouettes. Cleanliness and production still follow the continuous care timer.

The two staple dispensers remain the authored sugar and flour models. Milk and eggs reuse the artist's original trays, moved from `Kitchen.Upgrades.KitchenCounter.Upgrade` into `1ndFloor.Kitchen.Decoration.MilkBasket` and `EggBasket`. No second tray is cloned. Each folder contains the original `Stand` and an ingredient `Preview`; GardenWorld hides the preview during play because runtime stock owns the live item. The trays flank the sugar/flour sources as in Lemon Cake's `LVL_Game` (`BP_ItemSpawner6`, `BP_ItemSpawner13_2`). Their `OutputPath` entries in `Configs/Garden` control visibility with the cow/chicken upgrades. `GardenProduce1` on the reference bakery's animal anchors places the output and its prompt in the kitchen; `GardenCare` and the animal anchor remain in the greenhouse. These basket moves and attachment positions are place-only edits and must be saved with the place.

`AnimalPrompts` creates separate care and output targets. `BuildingHandler` validates Harvest distance against `AnimalProduce`, while care validates against the animal. Both targets use the same server-owned garden node; no duplicate pantry supply is created. Pickup animation originates at the basket. A carried source item can be put back with E, and that source does not create another portion while its item is carried.

Milk and eggs have one available portion and a three-second production interval; honey has one portion and a five-second interval at the hive. These values and the kitchen positions come from the installed Lemon Cake build 6596857 data. Brushing takes one second; the existing 120-second cleanliness curve and brush upgrade remain. When cleanliness expires, an uncollected animal product disappears and production pauses until brushing. Existing excess animal stock is moved into Pantry when the node is initialized, preserving saved inventory. Plant capacity and timing retain the existing cake-game tuning. This reproduces the source locations and production rules, not every original animation or global timer phase.

`VacantView` also captures the configured animal output folders outside `Upgrades`. It hides their stands and preview ingredients on unclaimed plots and after release; claiming restores authored properties before `GardenWorld` takes ownership.

## Guest movement

`CustomerViewHandler/Guest` moves every street pedestrian and cafe guest on the shared 10 Hz tick. Humanoid `AutoRotate` stays off: an owned `AlignOrientation` turns the body toward a heading that rotates at most `Configs/Guests.TurnRate` degrees per second, so physics rounds each tick's heading step instead of snapping. The heading aims `LookAhead` studs further along the route and legs hand over at each corner's bisector, so corners become short arcs; `Humanoid:Move` walks along the heading. Pace eases with `Acceleration` and `Deceleration`, drops while the body faces away from its path (turn first, then stride), and on routes with a look-at target slows over the final `SlowdownDistance` studs before the guest stops and turns to face it. Routes without a look-at keep their pace, so a route started from the arrival callback continues without a stop. `Street` spaces the crowd through the guest's `SpeedLimit` rather than writing `WalkSpeed`.

Walk playback follows the guest's pace against `Avatar.WalkReferenceSpeed`; 9 studs per second keeps planted feet still on a default R15 rig. Idle, walk, and sit crossfade over `Avatar.AnimationFadeTime`. A seating guest first turns to the chair's facing at the normal turn rate, so the seat tween lowers the body instead of spinning it. The seated state is enabled in the same frame as the explicit sit, so Roblox's touch-to-sit cannot apply its default weld pose first. The facing constraint is disabled while the weld owns the pose; standing up hands orientation back from the body's current facing.

## Reusable hints and tutorial

`Shared/Tutorial/Navigation` redirects an unrelated open page to its close/back button while retaining server-owned tutorial progress. Required recipe pages and the evening Report/Menu flow keep their intended targets. During the active introduction, opening Upgrades no longer replaces the current task with the optional upgrade lesson. Close targets resolve the visible, interactable `Exit` or `CloseButton` through `UIHandler`; Inventory, Report, and Upgrades prefer the shared `BakeryMenu` header. Page locks and hidden controls are respected. Closing the page immediately resolves the current gameplay step again.

`Shared/UI/Hint` owns reusable client hints for GUI and world targets. `HintGeometry` handles clipping/projection; `HintSurface` owns a transient, non-interactive overlay; `Configs/Hint` contains visual tuning and the two finger poses. Hints support target resolvers, responsive size, continuous automatic rotation, fixed angles, edge indicators, an authored world arrow beam, stable keys, priorities and optional duration. A single render callback presents the highest eligible priority and releases itself when no owners remain. The finger poses use a manually stepped Ripple tween with quintic easing: rest, press, brief hold, and a slower release. Smooth overlapping opacity avoids the old clamped crossfade, and each hint owns and destroys its motion. Suppressed hints pause their pose phase. The separate text/distance caption below the finger has been removed. `HintBeam` owns a local clone of `ReplicatedStorage.Assets.VFX.ArrowBeam`, connecting the player to the current 3D target; GUI, hidden and superseded hints disable it. Authored texture styling is retained, with repetition count adapted to distance. The original ArrowBeam was moved out of Workspace into this asset folder; save that place-only change separately from Script Sync source.

`Shared/UI/Tutorial/Focus` adapts tutorial targets to this public API instead of maintaining its own pointer and world spotlight. `Tutorial/Presenter` keeps the legacy tutorial ScreenGui disabled on every device: no card, Compact/Resume banner, handbook, or help menu is shown. An eligible goal announces its title once through the existing status toast, waiting for current feedback to finish. The saved collapsed preference still suppresses guidance; server-owned progress and existing debug controls remain. The introduction is enabled without resetting completed/skipped saves. Harvest guidance distinguishes animal care from kitchen output, and evening guidance uses the shared `BakeryMenu` header.

The introduction follows `Sweep → Cook → Serve → Clean`. `CleaningHandler:PrepareTutorial` prepares one authored spill only after the player's bakery is ready. The server waits for accepted mopping, no remaining spills, and the returned broom before cooking guidance begins. `PreparedFloor` is an additive action flag; existing cooking milestones and completed/skipped profiles are preserved without a version reset. Restarting with a selected recipe or a live batch bypasses this opening task, and a bakery without authored spills can continue cooking. Guests are held during `Sweep`, even if the player opens early. Ordinary cooking spills remain suppressed until the introduction ends.

World guidance uses the existing Beam until the exact target's actionable prompt is visible; then the finger points at its tappable plate without dimming the world. Another prop's prompt cannot replace the target. Waiting for mixing, baking, arrivals, or eating hides the pressing finger; the brief order-card lesson still highlights its card. Goal announcements settle for 0.25 seconds to avoid intermediate replication messages, and actionable goals repeat a short reminder after 18 seconds without replacing an active toast. Both intervals are configured in `Configs/Tutorial`.

`Shared/UI/Tutorial/GuestHighlight` gives the local player's protected tutorial guest a warm outline and translucent fill while `Arriving` or `Queued`. It resolves the session's exact `GuestId` inside the owned bakery's `Guests` folder; other players' guests and ordinary pedestrians are never selected. `TutorialHandler` owns cleanup and retries late model replication through its existing refresh callback. Seating, guest removal, collapsed guidance, or ending the introduction clears the highlight. Visual tuning lives in `Configs/Tutorial.GuestHighlight`; no server state or authored asset is changed.

`Shared/UI/StatusLayout` binds the authored status frame through `UI/App`. `Configs/Notifications` owns viewport breakpoints, padding, typography, and dimensions: at most 240 by 32 pixels on compact viewports, 360 by 48 on wide viewports. Decorative tag/lines are hidden. Layout responds to the screen's available size and shares the existing toast animation, state, and cleanup owner; no second notification system is created.

`hinttest` previews GUI/world guidance through the server-authorized Cmdr `TutorialDebug` group and the one-way `Bus.Hints.Debug` packet. `HintDebugHandler` owns the preview lifetime independently of the tutorial. `tutorialtest` aliases the existing progress-reset command; it changes tutorial progress, whereas `hinttest` does not. See [HINTS.md](HINTS.md) for the API, examples, commands and verification limits.

Occupied-table tutorial targets retain their exact seat frame when a dish model is present. Hint destruction clears visibility, bounds, and occlusion query state as well as releasing owned resources.

`HintAnimation` owns the manually stepped finger FSM, with named `Rest`, `Press`, `Hold`, and `Release` states and explicit next-state links in `Configs/Hint.FingerPhases`. Each hint composes this animation with its surface and beam; suppression pauses the animation, changing target identity resets it, and destruction releases it. Target resolution uses distinct GUI/world records. GUI focus, world projection/occlusion, and finger placement have separate functions with one shared frame context. `HintGeometry.Inset` owns safe-region shrinking, and ancestor visibility is checked by one flat predicate. The existing common render callback remains the sole scheduler; an ECS or a second handler loop is unnecessary for this fixed presentation pipeline.

Hint sizes, rotation limits, animation limits, shade color, occlusion thresholds, beam retry/texture limits, and tutorial/debug offsets live in `Configs/Hint`. Geometry tolerances remain named local constants. Cmdr preview modes use a typed dispatch table; presentation selection and lifetime cleanup have separate owners. Disabling occlusion or switching to GUI guidance clears the previous world-obstruction result.

## Developer panel

The developer panel uses English for labels, confirmations, status, and server responses.

`AdminPanelHandler` creates an owned developer overlay, opened with **F4**, **/admin**, or its **ADMIN** button. It does not replace authored `MainGui` screens. Player selection is limited to the current server; the panel supports status inspection, exact coin grants/balance replacement (without paid multipliers), XP, pantry stock, upgrade grants/budget, tutorial restart/skip, day transitions, hand cleanup, respawn, and full client data resynchronization. Actions call the existing owning handlers, preserving their signals, caches, state machines, and proxy writes.

Tutorial actions report a refusal while `Configs/Tutorial.Enabled` is false; the panel does not override the game's global tutorial switch. Day actions retain the existing phase/menu requirements and report refusals instead of forcing invalid state transitions.

`AdminHandler` authorizes every `Bus.Admin.Request` on the server. Published servers use the existing UserId allowlist in `ServerScriptService/Cmdr/Admin.luau` (currently `codebykoi` and `funseti`); add another developer's numeric UserId there and deploy the source change. Studio permits local test players. Roblox edit/collaboration permissions are not automatically treated as runtime admin access. The replicated `AdminPanelAccess` attribute controls presentation only and never authorizes a mutation.

Every panel mutation requires an expiring, one-use server confirmation bound to its executor, target Player instance, action, and amount. Requests validate finite integer quantities, action-specific limits, profile readiness, and pending resets; executor throttles and target locks prevent overlapping panel operations. Unknown actions and arbitrary data paths are rejected. The server Output records attempts/results with executor and target IDs; the panel exposes the last 30 results from this server's memory, not a durable cross-server audit service. Offline edits, bans, receipt grants, and arbitrary code execution are not exposed.

Progress reset uses `DataHandler:RequestProgressReset`: save the pending marker, end the session, and apply new-player defaults before `PlayerReady` on rejoin. It now starts with normal starter cash rather than an upgrade budget. Paid passes, skins, receipt deduplication, and `Stats.RobuxSpent` survive. The separate upgrade-budget action remains available. `DataHandler:ResendSnapshot` flushes preceding deltas and resends both stores using the existing snapshot/revision channel.

For isolated Studio QA, set the attribute `AdminTestMockData = true` on **ServerScriptService.Handlers.DataHandler** in Edit mode before starting Play, then remove it after stopping. `DataHandler` honors it only in Studio and uses ProfileStore.Mock; the configured live store and saving policy remain unchanged. The panel shows `STUDIO MOCK` when this mode is active. Ordinary Studio Play still saves real data when `StudioSavingEnabled` is true. Reset/rejoin persistence must be checked separately: a fresh Play session does not retain the in-memory mock store.

## Validation workflow

- `rokit.toml` pins Selene, StyLua, luau-lsp, Wally, and wally-package-types. Run tools through Rokit from the repository root.
- `scripts/check.ps1` is the verification gate: it regenerates the sourcemap, runs `selene .`, fails if any first-party `.lua`/`.luau` file does not start with `--!strict` (files matching `luau-lsp.ignoreGlobs`, the Wally packages and vendored libraries, are exempt), then runs the pinned analyzer over every source root: `luau-lsp analyze --platform roblox --definitions <globalTypes.PluginSecurity.d.luau> --sourcemap sourcemap.json --settings .vscode/settings.json ReplicatedFirst ReplicatedStorage ServerScriptService ServerStorage StarterCharacterScripts StarterPlayerScripts`. Definitions are resolved from `.zed/.cache` first, then the luau-lsp extension's Cursor/VS Code global storage; pass `-Definitions` to use another copy.
- Analysis uses luau-lsp's default type solver, matching the editor. Two shared shims exist because of it: `BaseStats.StatKey` is an explicit key union (no `keyof`), and `Shared/UI/Scope.luau` wraps `Flux.scope` for callbacks that return nothing. Flux selectors (`Find.Path`, `Find.Child`) are given plain signatures where they are used.
- Every first-party module is `--!strict`, so Studio's Script Analysis checks it strictly too. Three solver limits shape strict code here: a runtime-resolved `require` (Crystal's handler discovery, Cmdr's generated `CmdrClient`) is written `(require :: any)(module)` because strict mode rejects paths it cannot resolve; an instance built with `setmetatable` is only assignable to its own class type, so a field holding one uses that type (`Building.FoodVisual: FoodSurfaceView.FoodSurfaceView?`) instead of a structural interface; and reassigning a `T?` local inside `if not x then` does not narrow it afterwards, so use `existing or create()` or an early return.
- The editor runs Roblox's live FFlags while the CLI enables all stable flags, so the editor can be stricter about missing optional table fields. Config-style inputs therefore get their own input type (for example `StateMachine.StateDefinition`, the registry `Definition` types) rather than reusing the fully-populated runtime type.
- `.vscode/settings.json` and `selene.toml` exclude the Wally directories and the vendored libraries from diagnostics and lint. DataModel diagnostics use luau-lsp's default `strictDatamodelTypes = false`; the filesystem sourcemap cannot describe place-only assets such as `ReplicatedStorage.Assets`. Zed explicitly uses the same setting. This does not disable `--!strict` Luau checking; authored instances can be declared as an `AuthoredScreen`-style intersection type at the point of use.
- Formatting follows StyLua defaults; `.styluaignore` mirrors the lint exclusions. The `--[[ Section ]]--` header comments are rewritten by StyLua, so a repo-wide `stylua --check` is not part of the gate.
- The luau-lsp Studio companion plugin talks to the editor on port `3668` (`luau-lsp.studioPlugin.port`), shared with the other projects the Studio plugin is configured for, with `maximumRequestBodySize` raised to `50mb` because this place's DataModel dump exceeds the 3 MB default. Only one workspace can own the port at a time.

## Zed on Windows

Install Zed's `Luau` extension (`4teapo/zed-luau`), run `rokit install`, then `scripts/setup-zed.ps1`. The setup script caches Roblox PluginSecurity definitions and API docs in the ignored `.zed/.cache` directory and installs `4teapo/luau-lsp-proxy` v0.1.0 into the Luau extension's work directory. Use `-Refresh` to refresh these downloads. `scripts/check.ps1` can then run without VS Code or Cursor installed.

`.zed/settings.json` uses the Rokit `luau-lsp` and `stylua` commands from PATH, enables workspace diagnostics, and mirrors the project's vendor exclusions. DataModel diagnostics match VS Code and the CLI; enabling `strictDatamodelTypes` without a complete Studio tree reports missing place-only children. Zed uses stable CLI flags without live Roblox flag downloads or the experimental solver. StyLua runs on an explicit format command and respects `.styluaignore`; saving alone does not reformat existing section comments.

The Studio companion connects through the proxy on port `3668`. The proxy accepts compressed DataModel updates; the VS Code `maximumRequestBodySize` setting does not apply to it. Close the other editor's Luau workspace before using this port in Zed.

Use `task: spawn` for the project tasks in `.zed/tasks.json`: tool/package installation, Zed setup, the full check gate, and sourcemap generation. Zed's Luau extension does not run the VS Code sourcemap generator. After adding, removing, moving, or renaming scripts with Studio's Script Sync inactive, run `Regenerate sourcemap` (the check and package tasks also regenerate it). Source-content edits do not require regeneration. The generator and Selene exclude Zed's generated definitions from game source.
